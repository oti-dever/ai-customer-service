# 类似产品调研记录

> 调研对象：飞书文档 `AI客服使用说明` + 安装包 `D:\AI客服[2025-06-12]`
>
> 记录时间：2026-06-26

## 1. 调研目标

梳理这个类似产品的能力边界、运行架构、平台接入方式和知识库形态，为后续主线设计提供参考。

## 2. 主要结论

1. 这是一个 Windows 桌面端 AI 客服聚合工具，主体形态是 `Electron + 本地服务 + 网页注入扩展`。
2. 产品重点不是单一平台，而是多平台客服聚合，已覆盖或明确提到的平台包括：
   - 千牛工作台
   - 抖店飞鸽
   - 快手小店
   - 拼多多客服
3. AI 能力主要通过外部大模型和知识库接入完成，文档中明确提到：
   - Deepseek / OpenAI 兼容接口
   - 豆包大模型
   - Coze 智能体知识库
   - 微信机器人
4. 该产品的核心竞争点是“在平台网页里模拟人工发送”，而不是显式机器人接待。
5. 知识库不是单一文本，而是按店铺目录组织，通常由：
   - `店铺知识库.txt`
   - `商品列表.xlsx`
   - `问答列表.xlsx`
   组成。

## 5. 安装包静态分析

### 5.1 目录结构

安装包包含：

- `resources/app.asar`
- `resources/crx`
- `resources/知识库`
- `resources/kefuServe.exe`

这基本表明：

- `app.asar` 是 Electron 主应用
- `crx` 是浏览器扩展脚本
- `kefuServe.exe` 是本地服务进程
- `知识库` 是内置模板数据

### 5.2 主进程

`app.asar` 中的 `package.json` 指向：

- `main: ./out/main/index.js`

主进程能看到的关键行为：

- 启动 `resources/kefuServe.exe`
- 或按配置启动 `src/python/server.py`
- 注册窗口控制 IPC
- 使用 `electron-store`
- 通过本地服务和前端桥接消息通信

### 5.3 预加载桥

`out/preload/index.js` 里暴露了两个全局对象：

- `chrome2`
- `pyapi`

这说明页面脚本与主进程/服务之间是通过预加载桥完成双向通信的。

## 6. 平台接入方式

### 6.1 浏览器扩展注入

`resources/crx/manifest.json` 的 content scripts 只匹配：

- `*.jinritemai.com`
- `*.kwaixiaodian.com`
- `*.pinduoduo.com`

对应的脚本文件为：

- `js/dy.js`
- `js/ks.js`
- `js/pdd.js`

这说明抖店、快手、拼多多属于同一类“网页注入接入”。

### 6.2 千牛工作台

千牛并不在这个扩展匹配列表里，但文档和知识库模板都明确支持千牛，推测其接入链路与网页注入不同，更可能走桌面端或本地服务适配。

## 7. 知识库形态

### 7.1 目录约定

主进程里知识库读取路径固定在：

- `resources/知识库/<店铺目录>/店铺知识库.txt`
- `resources/知识库/<店铺目录>/商品列表.xlsx`
- `resources/知识库/<店铺目录>/问答列表.xlsx`

### 7.2 模板目录

安装包内置了多个示例目录，例如：

- `千牛工作台_有求必应羊羊_王刚`
- `即时零售_软1`
- `抖店飞鸽_snrt`
- `软件店铺示例`

### 7.3 推断

这类知识库更像“结构化店铺配置 + FAQ + 商品表”的组合，而不是纯向量库。RAG/模型回复只是其上一层能力。

## 8. 消息与页面行为

### 8.1 消息类型

静态脚本中可见的消息类型包括：

- `msg`
- `order`
- `goods`
- `isCustomer`
- `转接`
- `图片`

### 8.2 页面抓取特征

脚本明显使用了页面 DOM 选择器和内容识别来判断会话消息、商品卡片、图片消息和转接动作。

可见的特征关键词包括：

- 抖店：`image-msg`、`.good-card`、`ql-editor`
- 快手：`.SendBox-Editor`、`.SessionBar`
- 拼多多：`.LoginUserInfo-mainT`、`.good-card`、`.image-msg`

这说明它不是协议级接入，而是页面层自动化和 DOM 解析。

## 9. 架构判断

可归纳为：

1. Electron 桌面壳负责 UI、窗口、配置和本地资源。
2. 本地服务进程负责业务编排、知识库处理和任务调度。
3. 浏览器扩展负责挂载到各电商网页，读取消息并执行输入/发送动作。
4. `pyapi` / `chrome2` 负责把页面层、主进程、本地服务串起来。

## 10. 风险与边界

1. 这是静态分析结果，页面脚本大量混淆，部分细节只能做推断。
2. 千牛链路不是同一套 CRX 注入逻辑，后续要单独确认。
3. 目前没有运行外部安装包，只做了目录和源码层面的静态检查。
4. 文档和安装包都强调“模拟人工”，这意味着真实效果依赖页面结构稳定性。

## 11. 后续建议

1. 继续拆 `out/main/index.js`，把所有接口地址和任务流整理成表。
2. 继续拆 `out/preload/index.js`，把 `pyapi` / `chrome2` 的消息协议整理成契约文档。
3. 继续拆 `dy.js` / `ks.js` / `pdd.js`，整理成“DOM 特征 -> 消息类型 -> 动作”的映射表。
4. 如果后续要复刻类似能力，优先抽象“平台适配层”和“知识库层”，不要直接绑定某个平台脚本。
