# 拼多多平台静态拆解

> 来源：`D:\AI客服[2025-06-12]\resources\app.asar\out\crx\js\pdd.js`
>
> 记录时间：2026-06-26
>
> 分析方式：静态反混淆字符串与主路径阅读，未启动外部程序。

## 1. 结论概览

拼多多接入是典型的网页 DOM 注入适配，不是官方 API / SDK 接入。

主链路由几个函数组成：

| 函数 | 作用 |
|---|---|
| `y()` | 读取当前最新一条消息，并分类为文本、图片、商品、订单、线索、系统通知等 |
| `K(text)` | 向回复输入框写入文本并点击发送 |
| `N(name)` | 执行转接到指定客服/对象 |
| `q(name)` | 执行按组转接，本质调用 `N(name, "group")` |
| `j(task)` | 执行命令型任务，目前主要识别 `[转接组]` 和 `[转接]` |
| `A()` | 消费 `new-task` 队列，切换会话后执行文本或命令 |
| `J()` | 扫描未读会话并点击进入 |
| `_()` | 主轮询循环，负责检测消息、去重、上报 |
| `g(node)` | 判断一条消息是否来自顾客 |
| `I(node)` | 从普通文本消息节点提取 `time/content` |

## 2. 与主进程的消息协议

### 2.1 店铺信息上报

脚本启动后会反复尝试读取：

- `.nickname`

成功后上报：

```js
pyapi.sendMessage("to-renderer", {
  to: "main",
  type: "updateShopInfo",
  shopName: "拼多多",
  kefuName: "<.nickname innerText>",
  platform: "pdd"
})
```

### 2.2 新消息上报

消息上报统一走：

```js
pyapi.sendMessage("to-renderer", {
  to: "main",
  channel: "new-msg",
  data: {
    shopName: G,
    kefuName: "-",
    platform: "pdd",
    data: [
      { name, time, content }
    ]
  }
})
```

其中 `G` 是启动时读取到的店铺/客服名。

### 2.3 接收主页面任务

脚本监听：

```js
pyapi.onMessage("update-message", callback)
```

识别两类消息：

| 条件 | 行为 |
|---|---|
| `type == "update-monitor" && flag == "add"` | `p = true`，启动主轮询 `_()` |
| `type == "update-monitor" && flag == "del"` | `p = false`，清空去重状态 `b = {}` |
| `type == "new-task"` | 将 `task` 推入队列 `P` |

## 3. 最新消息分类 `y()`

入口节点：

```css
.msg-list li:last-child
```

脚本先默认 `isCustomer = true`，如果最新消息节点里包含：

```css
.cs-item
```

则把 `isCustomer` 置为 `false`。也就是说，`.cs-item` 被它视为客服侧消息标记。

分类规则：

| DOM 特征 | 输出类型 | 输出内容 |
|---|---|---|
| `.image-msg` | `pic` | `.image-msg img` 的 `src` |
| `.good-card` | `goods` | `[咨询商品]` + `.good-card .good-id` 去掉“复制” + `.good-card .good-name` |
| `.kwaishop-cs-BizOrderCard` | `order` | `.order-card` 的 `innerText` |
| `.kwaishop-cs-bizBuyerFromCard` | `clue` | `.kwaishop-cs-bizBuyerFromCard-itemInfo-right-title` 的 `innerText` |
| `.buyer-item` | `msg` | 空内容，仍标为顾客消息 |
| `.msg-system` | `notice` | 系统通知 |
| 未命中 | 空类型 | `{ type: "", content: "", isCustomer }` |

注意：脚本里出现大量 `kwaishop-*` class 名，这不代表快手平台，而是该拼多多客服页里复用或混入了类似命名的组件 class。当前记录只按脚本实际选择器保存。

## 4. 普通文本消息提取

普通文本消息不是从 `y()` 里直接提取，而是在主轮询 `_()` 中扫描消息列表：

```css
div[id*="cs-common-message-list-item"]
```

顾客消息判断：

```css
.kwaishop-cs-LayoutDefaultWrapper__isMine
```

`g(node)` 返回 `!node.querySelector(".kwaishop-cs-LayoutDefaultWrapper__isMine")`，即没有 `isMine` 标记就视为顾客消息。

文本和时间提取：

| 字段 | 选择器 |
|---|---|
| `content` | `.kwaishop-cs-BizTextCard` |
| `time` | `.kwaishop-cs-LayoutDefaultWrapper_sendItem.kwaishop-cs-LayoutDefaultWrapper__time` |

扫描逻辑从消息列表尾部往前遍历，遇到非顾客消息就停止；因此它只上报最近连续的一段顾客消息。

## 5. 消息去重与特殊类型前缀

脚本用全局对象 `b` 保存上一条已上报内容。普通文本按 `time + content` 去重；特殊卡片类型按 `b.content` 去重。

特殊类型会转成文本前缀：

| 原始类型 | 上报内容前缀 |
|---|---|
| `pic` | `[图片]` |
| `goods` | `[商品]` |
| `order` | `[订单]` |
| `clue` | `[线索]` |

例如商品卡片最终会上报：

```text
[商品][咨询商品]<商品ID> <商品名>
```

图片消息最终会上报：

```text
[图片]<图片URL>
```

## 6. 监控循环

主循环 `_()` 的关键行为：

1. 先调用 `J()`，扫描会话列表里的未读标记并点击进入。
2. 再消费任务队列 `A()`。
3. 如果监控开关 `p` 为 `false`，停止后续检测。
4. 调用 `y()` 读取最新消息。
5. 如果不是顾客消息，延迟后继续轮询。
6. 如果类型为空或 `notice`，忽略并继续轮询。
7. 如果是特殊类型，生成带前缀的一条消息并上报。
8. 如果是普通文本，则从当前消息列表尾部向前收集连续顾客消息并上报。
9. 轮询间隔大约 2 秒。

异常分支里也会继续 `setTimeout(_, 8000)` 左右重试。

## 7. 未读会话点击 `J()`

会话扫描选择器：

```css
.SessionListGroupItem .SessionListGroupItem-select\"
```

未读标记：

```css
.SessionBaseCard-unread-rot
```

如果某个会话节点包含未读标记，则点击：

```css
.SessionBaseCard-Static
```

静态观察：这里的会话选择器字符串尾部含转义引号，可能是源码压缩/混淆后的结果，也可能依赖页面实际 DOM 字符串拼接。后续真实 PoC 要优先校验这一段。

## 8. 任务执行 `A()`

任务来自 `P` 队列，每次 `P.shift()` 取一条。

任务格式可推断为：

```js
{
  name: "<会话用户名>",
  type: "text" | "cmd",
  content: "<回复内容或命令>"
}
```

如果任务里有 `name`，且当前会话不是该用户，会先尝试切换会话：

| 用途 | 选择器 |
|---|---|
| 当前用户名 | `.LoginUserInfo-mainTitle-text` |
| 会话列表容器 | `.SessionListGroupItem` |
| 可选会话项 | `.SessionListGroupItem-select\"` |
| 会话名称 | `.SessionBaseCard-topHeadName` |

任务类型：

| `type` | 行为 |
|---|---|
| `text` | 调用 `K(content)` 输入并发送 |
| `cmd` | 调用 `j(task)` 执行命令 |
| 其它 | 记录“不受支持的消息类型” |

## 9. 发送文本 `K(text)`

输入框：

```css
#replyTextarea
```

发送按钮：

```css
.reply-footer .send-btn
```

执行步骤：

1. `querySelector("#replyTextarea")`
2. 设置 `element.value = text`
3. 派发 `new InputEvent("input", { bubbles: true })`
4. 等待约 0.5 秒
5. 点击 `.reply-footer .send-btn`
6. 再等待约 0.5 秒

这说明发送动作依赖页面前端框架监听 `input` 事件，而不是只改 DOM 值。

## 10. 转接命令

命令入口 `j(task)` 只识别：

| 内容前缀 | 行为 |
|---|---|
| `[转接组]` | 去掉前缀后调用 `q(name)` |
| `[转接]` | 去掉前缀后调用 `N(name)` |

转接入口：

```css
.transfer-chat-wrap
```

转接弹窗表格：

```css
div[aria-label="转移会话"].tranform-chat-dialog tbody
```

候选行：

```css
tr.el-table__row
```

确认按钮：

```css
.item-btn-transfer
```

匹配规则：

- 对每一行取 `childNodes[0]` 和 `childNodes[7]`
- 只要任一列 `innerText == name`，点击该行最后节点下的 `.item-btn-transfer`
- 如果没有匹配项，打印“没找到客服”，并点击弹窗父节点关闭

静态观察：`q(name)` 会调用 `N(name, "group")`，但当前可见主路径里 `N` 没明显按第二参数切换搜索维度。真实运行时需要校验“转接组”和“转接客服”是否实际区分。

## 11. 对我们拼多多 PoC 的建议

### 11.1 最小可行采集链路

优先实现只读采集，不做自动发送：

1. 定位会话列表和当前会话区。
2. 读取 `.LoginUserInfo-mainTitle-text` 作为当前用户名。
3. 从 `div[id*="cs-common-message-list-item"]` 尾部向前采集连续顾客消息。
4. 用 `.kwaishop-cs-LayoutDefaultWrapper__isMine` 判断是否客服侧消息。
5. 文本消息只提取 `.kwaishop-cs-BizTextCard` 和时间节点。
6. 对图片、商品、订单、线索先输出 `message_type`，正文保留 `raw_text/raw_url`。

### 11.2 统一模型建议

建议不要直接沿用 `[图片]`、`[商品]` 这种前缀作为内部模型，而是转成：

```json
{
  "platform": "pdd",
  "direction": "inbound",
  "message_type": "text | image | product | order | lead | notice | unknown",
  "sender_role": "customer | agent | system",
  "content": "...",
  "raw": {
    "selector": "...",
    "html_text": "...",
    "asset_url": "..."
  },
  "confidence": "dom_exact | dom_partial | unknown"
}
```

### 11.3 风险点

1. 页面 class 名高度脆弱，尤其是 `kwaishop-*`、`SessionBaseCard-*`、`cs-common-message-list-item`。
2. 会话选择器里存在疑似异常转义引号，需要真实页面验证。
3. 自动发送依赖 `InputEvent`，后续若做人工确认，也应只回填草稿，不默认点击发送。
4. 商品/订单/线索卡片只提取可见文本，缺少稳定 ID 时要把原始 DOM 文本一起存入 `raw`。
5. 轮询间隔固定，真实 PoC 应加入页面可见性、登录状态、选择器缺失等降级状态。

## 12. 后续验证清单

真实页面 PoC 时优先验证：

- `.msg-list li:last-child` 是否稳定存在。
- `.cs-item` 是否确实代表客服侧消息。
- `.kwaishop-cs-LayoutDefaultWrapper__isMine` 是否稳定代表自己发送。
- `#replyTextarea` 是否是当前有效输入框。
- `.reply-footer .send-btn` 是否会直接发送，是否需要人工确认保护。
- `div[id*="cs-common-message-list-item"]` 是否包含完整消息历史。
- `.good-card`、`.order-card`、`.kwaishop-cs-bizBuyerFromCard` 是否覆盖主要卡片类型。
- 未读标记 `.SessionBaseCard-unread-rot` 是否稳定。
