# 邮件服务实现方案

日期：2026-07-13

## 1. 背景

聚合客服真实链路里，客户有时会索要链接、下载地址、资料地址或外部页面。但电商平台通常不允许客服直接发送外部链接，直接在聊天窗口发送 URL 可能触发风控、屏蔽或账号风险。

因此需要在 AI 客服后台增加邮件服务能力：当 AI 意图路由识别出客户需要链接或资料时，程序不直接在平台聊天中发送外链，而是引导客户提供邮箱，并通过邮件服务发送内容。邮件发送成功后，再在平台聊天里提醒客户注意查收邮箱。

首版先实现最小闭环：

1. 客户端后台提供邮件服务配置界面。
2. 支持选择邮箱类型，例如 QQ 邮箱、Gmail、自定义 SMTP。
3. 用户填写发件邮箱和授权码，保存配置。
4. Python 服务端集中实现 SMTP 邮件发送能力。
5. 首版邮件内容固定：
   - 主题：`hi`
   - 正文：`你好`
6. 后续再接入链接模板、订单资料、附件、机器人/店铺维度配置和正式 Workflow。

## 2. 设计目标

首版目标：

1. 在客户端 AI 客服后台左侧导航新增“邮件服务”入口。
2. 提供邮件服务配置页，支持 QQ 邮箱、Gmail、自定义 SMTP。
3. 支持保存发件邮箱、授权码、SMTP 主机、端口、加密方式等配置。
4. 支持发送测试邮件，验证配置是否可用。
5. Python 服务端新增独立邮件模块，负责配置读写、SMTP 登录验证和邮件发送。
6. 聚合自动回复链路可在后续通过 Action Center 调用邮件服务。
7. 邮件能力和 UI 解耦：客户端只负责交互和调用接口，真正发送能力集中在 Python 服务端。
8. 敏感信息不写入日志，不在 UI 明文回显授权码。

## 3. 非目标

首版不做以下能力：

- 不实现复杂邮件模板编辑器。
- 不实现附件发送。
- 不实现 HTML 邮件。
- 不实现 OAuth2 登录。
- 不实现邮件发送队列、重试队列、失败补偿。
- 不实现多邮箱账号切换策略。
- 不实现按店铺、平台、机器人分别绑定不同邮箱。
- 不实现邮件发送历史列表。
- 不把真实外链内容接入邮件正文，首版正文固定为 `你好`。
- 不让 AI 直接决定邮件是否已经发送，只有程序收到邮件服务成功结果后才允许提示客户“已发送”。

## 4. 总体架构

```text
AI 客服后台 UI
  -> 邮件服务配置页
  -> IpcService HTTP/WebSocket 调用
  -> Python service email 模块
  -> SMTP 服务器
```

与 AI 回复链路的关系：

```text
客户消息
  -> Reply Intent Router
  -> intent = link_request
  -> Action Plan
      - 无邮箱：生成“请提供邮箱”的平台回复
      - 有邮箱：调用邮件服务发送邮件
  -> 邮件服务返回成功
  -> 聚合真实发送层给客户发“已发送到邮箱，请查收”
```

核心原则：

- AI 负责识别客户意图。
- Workflow / Action Center 负责决定是否调用邮件服务。
- Python 邮件模块负责真实 SMTP 发送。
- 聚合真实发送层负责给客户发平台消息。

## 5. 客户端后台 UI 设计

### 5.1 入口

在 AI 客服后台左侧导航新增：

```text
邮件服务
```

建议放在“机器人管理 / 知识库管理 / API 配置”附近，因为它属于自动回复业务能力配置。

### 5.2 配置页字段

首版配置项：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| 邮箱类型 | 下拉框 | `QQ邮箱` / `Gmail` / `自定义 SMTP` |
| 发件邮箱 | 输入框 | 例如 `xxx@qq.com` |
| 授权码 | 密码输入框 | QQ 邮箱授权码、Gmail App Password 或 SMTP 密码 |
| SMTP 主机 | 输入框 | QQ/Gmail 自动填充，自定义可编辑 |
| SMTP 端口 | 输入框/数字框 | 常用 465 / 587 |
| 加密方式 | 下拉框 | SSL / STARTTLS / None |
| 测试收件邮箱 | 输入框 | 用于发送测试邮件 |

邮箱类型预设：

| 邮箱类型 | SMTP 主机 | 端口 | 加密方式 |
| --- | --- | --- | --- |
| QQ 邮箱 | `smtp.qq.com` | `465` | SSL |
| Gmail | `smtp.gmail.com` | `587` | STARTTLS |
| 自定义 SMTP | 手填 | 手填 | 手选 |

### 5.3 操作按钮

配置页提供：

```text
[保存配置] [发送测试邮件]
```

行为：

- 保存配置：调用 Python 服务端 `/api/email/config`。
- 发送测试邮件：调用 Python 服务端 `/api/email/test`。
- 测试邮件内容首版固定：
  - 主题：`hi`
  - 正文：`你好`

### 5.4 UI 状态

页面状态建议：

- 未配置：提示“请先配置发件邮箱和授权码”。
- 已配置：展示邮箱类型、发件邮箱、SMTP 主机、端口、加密方式。
- 授权码已保存：只显示“已保存”，不回显原文。
- 测试中：按钮 disabled，显示“正在发送测试邮件...”。
- 测试成功：显示“测试邮件发送成功”。
- 测试失败：显示精简错误，例如认证失败、连接超时、收件邮箱格式错误。

## 6. Python 服务端设计

### 6.1 模块位置

建议新增：

```text
python/service/email_service.py
```

职责：

- 邮件配置模型。
- 配置保存和读取。
- SMTP 参数解析。
- SMTP 登录验证。
- 发送纯文本邮件。
- 错误归一化。

### 6.2 HTTP 接口

建议新增接口：

```text
GET  /api/email/config
POST /api/email/config
POST /api/email/test
POST /api/email/send
```

#### GET /api/email/config

返回当前邮件配置，授权码不返回明文。

示例响应：

```json
{
  "status": "success",
  "config": {
    "provider": "qq",
    "sender_email": "demo@qq.com",
    "smtp_host": "smtp.qq.com",
    "smtp_port": 465,
    "security": "ssl",
    "auth_code_saved": true,
    "enabled": true
  }
}
```

#### POST /api/email/config

保存配置。

示例请求：

```json
{
  "provider": "qq",
  "sender_email": "demo@qq.com",
  "auth_code": "xxxxxx",
  "smtp_host": "smtp.qq.com",
  "smtp_port": 465,
  "security": "ssl",
  "enabled": true
}
```

示例响应：

```json
{
  "status": "success"
}
```

#### POST /api/email/test

发送测试邮件。

示例请求：

```json
{
  "to": "receiver@example.com"
}
```

服务端使用已保存配置发送：

```text
subject = hi
body = 你好
```

示例响应：

```json
{
  "status": "success",
  "message": "sent"
}
```

失败响应：

```json
{
  "status": "error",
  "error": "smtp_auth_failed",
  "detail": "邮箱认证失败，请检查授权码"
}
```

#### POST /api/email/send

首版也先发送固定内容，后续再扩展动态主题、正文和附件。

示例请求：

```json
{
  "to": "customer@example.com",
  "scene": "link_request",
  "conversation_id": 123,
  "trace_id": "xxx"
}
```

首版服务端忽略动态正文，统一发送：

```text
subject = hi
body = 你好
```

示例响应：

```json
{
  "status": "success",
  "message_id": "local-uuid",
  "sent_at": "2026-07-13T10:00:00+08:00"
}
```

## 7. 配置存储

### 7.1 存储位置

建议 Python 服务端统一保存邮件配置，避免客户端和服务端各存一份。

可选方案：

1. 首版简单 JSON 文件：

```text
python/service/config/email_config.json
```

2. 后续迁入服务事实库或统一配置表。

首版建议 JSON 文件即可，改动最小。

### 7.2 配置结构

```json
{
  "enabled": true,
  "provider": "qq",
  "sender_email": "demo@qq.com",
  "auth_code": "encrypted-or-obfuscated",
  "smtp_host": "smtp.qq.com",
  "smtp_port": 465,
  "security": "ssl",
  "updated_at": "2026-07-13T10:00:00+08:00"
}
```

### 7.3 授权码处理

首版至少做到：

- 不写入普通日志。
- GET 接口不返回明文授权码。
- UI 不回显明文授权码。
- trace 中只记录 `auth_code_saved=true/false`。

更理想的做法：

- Windows 客户端环境可考虑 DPAPI。
- 或 Python 服务端使用本机派生密钥加密。
- 或后续接入系统凭据管理器。

如果首版来不及做强加密，也应明确这是本地单机配置，不能上传仓库，不能进入日志。

## 8. 邮件发送实现细节

### 8.1 SMTP 发送策略

Python 使用标准库即可：

```text
smtplib
email.message.EmailMessage
ssl
```

发送流程：

```text
读取配置
  -> 校验 enabled
  -> 校验 sender_email / auth_code / smtp_host / smtp_port
  -> 构造 EmailMessage
  -> 根据 security 选择 SMTP_SSL / SMTP + starttls
  -> login
  -> send_message
  -> 返回成功或错误
```

### 8.2 错误归一化

建议统一错误码：

| 错误码 | 含义 |
| --- | --- |
| `email_not_configured` | 未配置邮件服务 |
| `email_disabled` | 邮件服务未启用 |
| `invalid_recipient` | 收件邮箱格式不合法 |
| `smtp_connect_failed` | SMTP 连接失败 |
| `smtp_auth_failed` | SMTP 认证失败 |
| `smtp_send_failed` | SMTP 发送失败 |
| `smtp_timeout` | SMTP 超时 |
| `unknown_error` | 未分类错误 |

客户端只展示简短可理解信息，详细异常写服务日志，但不能包含授权码。

## 9. 与意图路由 / Workflow 的衔接

当前共享回复链路已经预留：

- `intent = link_request`
- `need_email`
- `ask_for_email`
- `email_service_required`
- `direct_external_link_blocked`

后续接邮件服务时建议流程：

### 9.1 客户索要链接但没有邮箱

```text
客户：发我链接
  -> intent = link_request
  -> missing_slots = ["email"]
  -> 不调用邮件服务
  -> 平台回复：平台不方便直接发链接，麻烦您提供一下邮箱，我这边发到邮箱里
```

### 9.2 客户提供邮箱

```text
客户：发到 xxx@example.com
  -> intent = link_request
  -> email = xxx@example.com
  -> Action Center 调用 /api/email/send
  -> 成功：平台回复“已经发到邮箱，请注意查收”
  -> 失败：平台回复“邮箱发送暂时异常，我这边帮您进一步处理”
```

关键限制：

- AI 不能自行声称邮件已发送。
- 只有 `/api/email/send` 返回成功后，聚合真实发送层才能发送“已发邮箱”的提示。
- 如果邮件服务未配置，应该转为人工处理或提示客服配置邮件服务。

### 9.3 阶段三：模板与业务内容扩展

阶段三的目标不是让 AI 自由生成邮件正文，而是让用户在后台维护确定的邮件模板，AI 只负责识别客户意图、补齐业务槽位并选择模板。程序根据模板 ID 执行邮件发送。

核心原则：

- AI 负责理解客户到底要什么，例如要图片、要看图地址、要粉丝群、要店铺资料、还是普通咨询。
- AI 返回结构化 JSON，不能直接决定“邮件已发送”。
- 程序负责校验邮箱、模板、服务状态和平台合规限制。
- 邮件主题、正文、外链、群号等业务内容来自用户维护的模板，不由 AI 临场编写。
- 平台聊天里不发送外部 URL，只能引导邮箱或提示查收。

#### 9.3.1 意图边界

“看图”相关表达必须拆分为不同意图，不能只按关键词触发图片库。

| 客户表达 | 正确意图 | 后续动作 |
| --- | --- | --- |
| `有实拍图吗` / `发张图看看` / `有没有图片` | `image_request` | 检索图片知识库，回复文字 + 图片 |
| `有没有看图地址` / `发我链接` / `店铺看图地址` | `email_link_request` | 不在平台发链接，引导客户提供邮箱 |
| `有没有极霸猫店铺的看图地址` | `email_link_request` + 已知模板 | 缺邮箱则询问邮箱，有邮箱则发模板邮件 |
| `有没有看图地址` 且上下文无法判断店铺 | `email_link_request` + 缺少模板槽位 | 追问客户具体要哪个店铺 |

因此，`看图地址`、`链接`、`网址`、`粉丝群`、`店铺地址` 这类表达应优先进入邮件资料流程；`实拍图`、`图片`、`照片`、`效果图` 这类表达才进入图片回复流程。

#### 9.3.2 邮件模板模型

邮件模板建议由 Python 服务端统一保存，客户端后台负责管理界面。首版可以继续使用本地 JSON 文件，后续再迁移到数据库。

建议模板字段：

```json
{
  "template_id": "jibamao_view_link",
  "name": "极霸猫店铺看图地址",
  "scene": "store_view_link",
  "subject": "极霸猫店铺，可进入粉丝群，进群有福利可看无码图哦",
  "body": "看图地址：【极霸猫】：http://47.99.124.86:5010/home/index?sysCode=90PE\n...",
  "aliases": ["极霸猫", "极霸猫店铺", "极霸猫粉丝群", "极霸猫看图地址"],
  "enabled": true,
  "platform_scope": [],
  "robot_scope": [],
  "store_scope": [],
  "updated_at": "2026-07-13T10:00:00+08:00"
}
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `template_id` | 稳定唯一 ID，Workflow 只传 ID，不传整段正文 |
| `name` | 后台展示名称 |
| `scene` | 业务场景，例如 `store_view_link`、`download_link`、`after_sales_material` |
| `subject` | 邮件主题，由用户维护 |
| `body` | 邮件正文，由用户维护，可包含 URL、群号等内容 |
| `aliases` | 用于 AI 和程序辅助匹配的别名 |
| `enabled` | 是否启用，停用模板不能被自动发送 |
| `platform_scope` / `robot_scope` / `store_scope` | 后续用于按平台、机器人、店铺限定模板可见性 |

当前已有 Word 文档内容可以作为批量导入来源。导入规则建议按 `主题：` 和 `正文：` 分块，每个分块生成一份模板，模板别名从主题和正文中的店铺名提取，用户导入后仍可在界面二次编辑。

#### 9.3.3 给 AI 的上下文

意图路由阶段可以给 AI 以下信息：

```json
{
  "recent_messages": [
    {"role": "customer", "content": "有没有极霸猫店铺的看图地址"},
    {"role": "assistant", "content": "亲，请提供一下邮箱哦"}
  ],
  "workflow_state": {
    "pending_intent": "email_link_request",
    "pending_template_id": "jibamao_view_link",
    "missing_slots": ["email"]
  },
  "template_catalog": [
    {
      "template_id": "jibamao_view_link",
      "name": "极霸猫店铺看图地址",
      "scene": "store_view_link",
      "aliases": ["极霸猫", "极霸猫店铺", "极霸猫看图地址"]
    },
    {
      "template_id": "yuzhaizhijing_view_link",
      "name": "御宅之径店铺看图地址",
      "scene": "store_view_link",
      "aliases": ["御宅之径", "御宅之径店铺", "御宅之径看图地址"]
    }
  ],
  "policy": {
    "direct_external_link_in_chat": false,
    "ai_must_not_claim_email_sent": true
  }
}
```

注意：

- `template_catalog` 只给模板 ID、名称、场景和别名，不建议把完整正文和真实 URL 都塞给 AI。
- 如果 AI 需要判断模板，依靠模板名称和别名即可。
- 邮件正文由程序在执行阶段按 `template_id` 读取，避免 AI 改写链接或串错店铺。

#### 9.3.4 AI 结构化返回

意图路由建议返回结构化 JSON：

```json
{
  "intent": "email_link_request",
  "confidence": 0.86,
  "business_object": {
    "type": "store",
    "name": "极霸猫"
  },
  "template_id": "jibamao_view_link",
  "email": "",
  "missing_slots": ["email"],
  "next_action": "ask_email",
  "customer_message": "亲，平台不方便直接发地址，麻烦您提供一下邮箱，我这边发到邮箱里哦",
  "reason": "客户索要极霸猫店铺看图地址，属于外链资料发送场景"
}
```

关键字段：

| 字段 | 说明 |
| --- | --- |
| `intent` | 意图，例如 `normal_question`、`image_request`、`email_link_request` |
| `confidence` | AI 判断置信度，低置信度不应自动执行发送动作 |
| `template_id` | 命中的邮件模板 ID，缺失时不能发送邮件 |
| `email` | 客户提供的邮箱，程序还需二次校验格式 |
| `missing_slots` | 缺失槽位，例如 `email`、`template` |
| `next_action` | 下一步动作，例如 `ask_email`、`ask_template`、`send_email`、`normal_reply` |
| `customer_message` | 需要在平台发送的追问或提示，不能包含外部 URL |

#### 9.3.5 Workflow 状态流转

典型流程一：客户明确店铺但没有邮箱。

```text
客户：有没有极霸猫店铺的看图地址
  -> AI 路由：email_link_request + template_id=jibamao_view_link + missing=email
  -> 平台回复：亲，平台不方便直接发地址，麻烦您提供一下邮箱，我这边发到邮箱里哦
  -> 保存 pending_workflow：等待邮箱，模板=jibamao_view_link
```

典型流程二：客户随后提供邮箱。

```text
客户：xxx@example.com
  -> AI 路由：继承 pending_workflow，识别 email
  -> 程序校验邮箱和 template_id
  -> Action Center 调用 /api/email/send，传入 template_id
  -> 邮件成功：平台回复“亲，资料已发送到您的邮箱，请注意查收。”
  -> 邮件失败：平台回复“亲，邮件发送暂时异常，我这边帮您进一步处理。”
```

典型流程三：客户只说“有没有看图地址”，上下文无法判断店铺。

```text
客户：有没有看图地址
  -> AI 路由：email_link_request + missing=template
  -> 平台回复：亲，我们这边有极霸猫、御宅之径、萌动彼岸等店铺资料，您具体要哪个店铺的呢？
  -> 保存 pending_workflow：等待模板/店铺
```

典型流程四：客户补充店铺。

```text
客户：极霸猫
  -> AI 路由：继承 pending_workflow，命中 template_id=jibamao_view_link
  -> 如果没有邮箱：继续询问邮箱
  -> 如果已有邮箱：进入邮件发送
```

#### 9.3.6 阶段三接口扩展

建议新增模板管理接口：

```text

POST   /api/email/templates
PUT    /api/email/templates/{template_id}
DELETE /api/email/templates/{template_id}
POST   /api/email/templates/import
```

建议扩展 `/api/email/send`：

```json
{
  "to": "customer@example.com",
  "scene": "store_view_link",
  "template_id": "jibamao_view_link",
  "conversation_id": 123,
  "trace_id": "xxx"
}
```

服务端发送前必须校验：

- 邮件服务已配置且启用。
- 收件邮箱格式合法。
- `template_id` 存在且启用。
- 模板适用范围包含当前平台、机器人或店铺。
- 模板主题和正文不为空。

#### 9.3.7 执行保护

程序侧必须保留硬性保护：

- 没有合法邮箱时不能调用邮件发送。
- 没有模板 ID 时不能调用邮件发送。
- 模板不存在、停用或不在适用范围内时不能调用邮件发送。
- 邮件服务失败时不能发送“已发送”提示。
- 平台聊天消息中如果包含 URL，应拦截或转为人工处理。
- AI 返回低置信度时，不自动执行邮件动作，应追问或走普通回复。
- AI 只能选择 `next_action`，不能绕过 Action Center 直接生成“邮件已发送”的回复。

## 11. 开发阶段计划

### 阶段一：邮件服务配置与测试发送

范围：

- 后台左侧新增“邮件服务”入口。
- 邮件配置页。
- Python `email_service.py`。
- `GET /api/email/config`
- `POST /api/email/config`
- `POST /api/email/test`
- 固定主题 `hi`，正文 `你好`。

验收：

- QQ 邮箱配置后可发送测试邮件。
- Gmail SMTP 配置后可发送测试邮件。
- 授权码不在 UI 明文回显。
- 日志不出现授权码。

### 阶段二：接入 Workflow / Action Center

范围：

- `link_request + email` 调用 `/api/email/send`。
- 邮件成功后，聚合发送层给客户发查收提醒。
- 邮件失败时不发送“已发送”承诺。
- trace 记录邮件动作结果。

验收：

- 客户要链接但没邮箱时，只询问邮箱。
- 客户提供邮箱后，能触发邮件发送。
- 邮件成功后才提示客户查收。
- 邮件失败时进入失败提示或人工处理路径。

### 阶段三：模板与业务内容扩展

范围：

- 邮件主题/正文模板管理，支持新建、编辑、删除、启用、停用。
- 支持一份或多份邮件草稿，用户可维护主题、正文、别名和适用场景。
- 支持从 `主题：` / `正文：` 格式的文档内容批量导入模板，导入后允许二次编辑。
- Reply Intent Router 接入模板目录，AI 根据最近聊天上下文、当前 Workflow 状态和模板别名返回结构化 JSON。
- 支持 `email_link_request` 意图下的槽位补齐：缺邮箱则问邮箱，缺模板/店铺则追问具体店铺。
- `/api/email/send` 支持按 `template_id` 发送邮件，邮件服务端根据模板 ID 读取主题和正文。
- 聚合真实发送层只负责执行 Action Center 结果：邮件成功后提示查收，失败时不承诺已发送。
- trace 记录模板选择、槽位缺失、邮件动作开始和邮件动作结果。

暂不纳入阶段三首批：

- 复杂富文本邮件编辑器。
- HTML 邮件和附件。
- 邮件发送历史完整列表。
- 多发件邮箱自动路由。
- 按平台/机器人/店铺绑定不同发件邮箱。

验收：

- 后台可以新建并保存“极霸猫店铺看图地址”等模板，主题和正文再次打开后可正常回填。
- 客户问“有没有极霸猫店铺的看图地址”时，不触发图片库发送，进入邮件资料流程。
- 客户明确店铺但没有邮箱时，自动回复询问邮箱。
- 客户随后发送邮箱时，系统继承上一轮 pending workflow，按已选模板发送邮件。
- 客户只问“有没有看图地址”且上下文无法判断店铺时，系统追问具体店铺，不直接发送邮件。
- 邮件发送成功后，平台聊天只提示客户查收邮箱，不出现外部 URL。
- 邮件发送失败时，平台聊天不出现“已发送”承诺。
- AI 返回的 `template_id` 不存在、停用或置信度过低时，不自动发送邮件。

## 13. 风险点

1. 授权码安全

   授权码不能进入日志、trace、Git 仓库。首版如果只是本地 JSON 保存，也必须加入忽略规则或放入已忽略的运行时目录。

2. SMTP 网络环境

   用户本机可能无法访问 Gmail SMTP，或被防火墙拦截。错误需要清晰提示。

3. 平台合规

   即使邮件发送成功，平台聊天里也不应出现外部 URL。只能提示“已发到邮箱，请查收”。

4. AI 承诺问题

   AI 不能决定邮件是否已经发送。邮件发送结果必须由程序动作返回。

5. Gmail 登录方式

   Gmail 普通密码通常不可用，用户需要 App Password；长期建议 OAuth2。

## 14. 推荐结论

建议先按“客户端配置页 + Python SMTP 服务 + 测试邮件”做第一版。邮件内容固定为 `hi / 你好`，先验证配置、发送、错误处理、安全脱敏和链路可用性。

等第一版稳定后，再把 `link_request` Workflow 接入邮件服务。阶段三建议优先做“邮件模板 + AI 结构化意图路由 + 槽位追问 + 按模板 ID 发送”的闭环，不建议一开始就做复杂富文本、附件、发送历史和多发件邮箱路由。

其中最关键的边界是：AI 只负责识别客户意图、选择模板和补齐槽位；程序负责校验模板、邮箱和服务状态，并在邮件服务返回成功后才提示客户查收。这样既能处理“有没有极霸猫店铺的看图地址”“有没有看图地址”这类不可预测表达，也能避免 AI 错发图片、错编链接或错误承诺邮件已发送。
