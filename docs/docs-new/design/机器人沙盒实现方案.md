# 机器人沙盒实现方案

日期：2026-07-09

## 1. 背景

当前机器人管理已经把模型、知识库、回复语气、常用称呼、自动发图、自动多条消息等策略收束到“机器人”实体中。真实聚合会话里可以通过手动“生成本条回复”或“AI 自动回复”验证效果，但这种验证方式有几个问题：

- 需要依赖真实客户会话，不适合频繁调试。
- 测试内容会混入真实聊天记录，容易影响客服判断。
- 难以连续模拟多轮咨询、短确认、追问、图片需求等场景。
- Prompt、知识库检索、图片素材推荐和多条消息策略调试成本较高。

因此需要在后台机器人列表中增加“测试回复”能力，点击后打开“机器人沙盒”界面。沙盒用于在不影响真实客户会话的情况下，按当前机器人配置模拟客户咨询并查看 AI 回复效果。

## 2. 设计目标

首版机器人沙盒目标：

1. 在“店铺机器人配置”列表操作列增加“测试回复”按钮。
2. 点击后打开独立“机器人沙盒”窗口或对话框。
3. 每个机器人拥有独立测试聊天历史。
4. 沙盒聊天区使用消息气泡布局：测试用户消息在右侧，AI 回复在左侧。
5. 底部包含“清空历史”按钮、输入框和“发送”按钮。
6. 发送测试问题后，使用当前机器人配置生成 AI 回复。
7. 沙盒回复链路尽量复用真实回复链路的 Prompt、知识库检索、图片素材检索和模型调用逻辑。
8. 沙盒消息不写入真实客户会话，不触发真实平台发送。
9. 支持清空当前机器人的沙盒测试历史。
10. trace 日志记录沙盒调用过程，方便调试 Prompt 和知识库命中。
11. 测试用户首版只发送文本消息，不支持上传图片。
12. 如果机器人开启 `allow_auto_send_images`，AI 回复支持从机器人绑定知识库的图片素材中选择图片，并在沙盒聊天区以图片消息展示。

## 3. 非目标

首版不做以下能力：

- 不发送真实平台消息。
- 不把沙盒消息混入 `MessageDao` 的真实客户消息表。
- 不做多机器人同屏对比。
- 不做团队共享测试集、评分体系或回归测试平台。
- 不做复杂变量模板。
- 不做测试用户图片上传和“客户发图”多模态测试。
- 不生成临时 AI 图片；AI 回复图片仅来自机器人绑定知识库中的已有图片素材。
- 不做沙盒消息云同步。

这些能力可在首版稳定后继续扩展。

## 4. 产品形态

### 4.1 入口

在 AI 客服后台“店铺机器人配置”列表的操作列中增加：

```text
测试回复
```

按钮与“编辑、复制、停用/启用、删除”同级。

建议操作列顺序：

```text
测试回复 / 编辑 / 复制 / 停用 / 删除
```

如果操作列宽度不足，可以将按钮压缩为：

```text
测试 / 编辑 / 复制 / 停用 / 删除
```

或后续改为“更多”菜单。首版优先保持按钮直观。

### 4.2 沙盒窗口布局

点击“测试回复”后打开：

```text
机器人沙盒 - {机器人名称}
```

布局从上到下：

```text
[机器人信息栏]
机器人：xxx
模型：xxx
知识库：xxx、xxx
策略：语气 / 称呼 / 自动发图 / 多条消息上限

[聊天区]
左侧气泡：AI 文本回复、AI 图片回复
右侧气泡：测试用户消息

[底部输入区]
[清空历史] [输入框................................] [发送]
```

聊天区行为：

- 按创建时间正序展示当前机器人的沙盒消息。
- 用户测试消息右侧展示。
- AI 文本回复在左侧气泡展示。
- 机器人允许自动发图且命中安全图片素材时，在文字气泡后追加左侧图片气泡。
- 图片气泡支持缩略图展示，点击后预览原图。
- 发送中展示临时状态，例如“AI 正在回复...”。
- AI 回复失败时展示错误气泡或状态提示。
- 支持滚动到底部。

底部输入区：

- “清空历史”：清空当前机器人的沙盒聊天历史。
- 输入框：输入测试问题。
- “发送”：保存测试用户消息并调用 AI 回复。

### 4.3 空状态

当前机器人没有测试历史时，聊天区展示空状态：

```text
暂无测试消息
输入一个客户问题，测试当前机器人的回复效果。
```

## 5. 数据存储

沙盒消息应单独存储，不复用真实客户消息表。

建议新增客户端本地表：

```sql
CREATE TABLE IF NOT EXISTS robot_sandbox_messages (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  robot_id TEXT NOT NULL,
  role TEXT NOT NULL,
  content TEXT NOT NULL DEFAULT '',
  content_type TEXT NOT NULL DEFAULT 'text',
  image_path TEXT NOT NULL DEFAULT '',
  metadata TEXT NOT NULL DEFAULT '{}',
  created_at TEXT NOT NULL
);

CREATE INDEX IF NOT EXISTS idx_robot_sandbox_messages_robot_time
ON robot_sandbox_messages(robot_id, id);
```

字段说明：

| 字段 | 说明 |
| --- | --- |
| `id` | 自增主键 |
| `robot_id` | 机器人 ID，每个机器人独立测试历史 |
| `role` | `user` / `assistant` / `system` |
| `content` | 文本内容 |
| `content_type` | 首版支持 `text`、`image` |
| `image_path` | `content_type=image` 时保存知识库图片素材的本地路径 |
| `metadata` | JSON 扩展字段，例如 trace_id、模型、知识库命中摘要、建议附图 |
| `created_at` | 创建时间 |

清空当前机器人历史：

```sql
DELETE FROM robot_sandbox_messages WHERE robot_id = ?;
```

### 5.1 metadata 建议

AI 回复消息的 `metadata` 可记录：

```json
{
  "trace_id": "xxx",
  "session_model_key": "doubao",
  "model": "xxx",
  "knowledge_status": "已检索到 3 条知识库片段",
  "knowledge_result_count": 3,
  "image_candidate_count": 2,
  "suggested_images": [
    {
      "asset_id": "img_xxx",
      "title": "keyboard_k87_black_red_front.png",
      "file_path": "D:\\ai-customer-service\\docs\\knowledge-base\\keyboard_k87_black_red_front.png",
      "score": 0.82
    }
  ]
}
```

首版 UI 可以先不完整展示 metadata，但 trace 和后续调试会用到。

AI 回复图片建议单独保存为沙盒消息：

```text
assistant / text  / 亲，这款是 K87 的实拍图哦~
assistant / image / D:\ai-customer-service\docs\knowledge-base\keyboard_k87_black_red_front.png
```

图片消息的 `metadata` 建议保存：

```json
{
  "asset_id": "img_xxx",
  "title": "keyboard_k87_black_red_front.png",
  "recommendation_reason": "客户明确询问 K87 实拍图",
  "risk_tags": "",
  "score": 0.82
}
```

## 6. 回复链路

### 6.1 基本流程

```text
点击发送
  -> 保存一条 role=user 的沙盒消息
  -> 读取当前 robot_id 对应机器人配置
  -> 读取该机器人的最近 N 条沙盒消息
  -> 最新 user 消息作为知识库检索主 query
  -> 按机器人 knowledge_base_ids 检索文档知识
  -> 按机器人 knowledge_base_ids 检索图片素材候选
  -> 构造 Prompt
  -> 调用机器人绑定的模型
  -> 保存 role=assistant、content_type=text 的沙盒文字回复
  -> 如果机器人允许自动发图且图片候选通过校验
       -> 保存 role=assistant、content_type=image 的沙盒图片消息
  -> 刷新聊天区
```

### 6.2 与真实回复链路的关系

真实聚合回复链路当前依赖：

```text
conversationId
  -> 最新入站快照
  -> 最近 10 条真实聊天记录
  -> 机器人运行时配置
  -> 知识库检索
  -> 图片素材检索
  -> Prompt
  -> 模型
```

沙盒链路不应该伪造真实 conversation，也不应该写真实消息表。建议抽象成两类上下文：

```text
真实会话上下文：
  - conversationId
  - latest inbound
  - recent real messages

沙盒测试上下文：
  - robotId
  - latest sandbox user message
  - recent sandbox messages
```

两类上下文最终都进入统一的回复构建能力：

```text
ReplyBuildInput
  - runtimeConfig
  - latestUserText
  - recentTurns
  - optionalImagePath
  - traceEntry
```

这样 Prompt、知识库检索、图片推荐和策略字段不会分裂成两套长期维护的逻辑。

### 6.3 沙盒运行时配置

沙盒不需要平台绑定解析，因为入口已经明确是某个机器人。

沙盒运行时配置规则：

```text
robot_id
  -> 读取机器人配置
  -> 如果机器人不存在：提示机器人已删除
  -> 如果机器人停用：允许测试，但 UI 提示“当前机器人停用，真实自动回复不会使用”
  -> 如果模型配置缺失：阻断测试并提示模型不可用
  -> 如果未绑定知识库：跳过知识库检索
```

是否允许测试停用机器人可以保留，因为调试时可能需要先停用再调整配置。真实自动回复仍要求机器人启用。

## 7. Prompt 与上下文

### 7.1 最近消息数量

沙盒默认取当前机器人最近 10 条沙盒消息进入大模型上下文，规则与真实聚合会话保持一致。

```text
最近 10 条沙盒消息
  -> role=user / assistant
  -> 按时间正序进入模型上下文
```

### 7.2 检索 query

沙盒知识库检索 query 优先使用最新测试用户消息。

```text
query 优先级：
1. 最新测试用户消息中的明确咨询问题
2. 如果是追问，可结合最近 1-2 条沙盒上下文补全指代
3. 如果只是“可以 / 好 / 嗯 / 行 / 谢谢”等短确认，先结合上一条 AI 沙盒回复判断是否需要继续；不需要继续时跳过知识库检索
```

### 7.3 多条消息策略

沙盒应遵守机器人策略：

- `allow_auto_send_multi_messages`
- `max_auto_send_messages`

但沙盒不真实发送消息，可以在聊天区中按多条 assistant 气泡展示。规则：

```text
模型返回一段文本
  -> 如果包含单独一行 ---MSG---，按该分隔符拆分
  -> 按 max_auto_send_messages 截断
  -> 做相似去重
  -> 每条作为独立 assistant 沙盒消息保存和展示
```

如果未开启多条消息，则忽略分隔符并合并为单条 assistant 消息。

## 8. AI 图片回复

首版测试用户暂不支持图片发送，但 AI 回复应支持图片消息，用于验证机器人自动发图策略和图片素材匹配准确率。

流程：

```text
测试用户发送文本
  -> 按机器人 knowledge_base_ids 检索图片素材
  -> 结合客户最新问题和沙盒历史解析目标商品/场景
  -> 生成 AI 文字回复
  -> 检查机器人 allow_auto_send_images
  -> 检查图片候选 should_attach、风险标签和本地文件
  -> 保存并展示 AI 图片消息
```

### 8.1 发送条件

只有同时满足以下条件时，沙盒才展示 AI 图片回复：

1. 机器人 `allow_auto_send_images = true`。
2. 客户最新测试消息明确需要图片，或现有图片推荐逻辑判断 `should_attach = true`。
3. 图片属于机器人绑定知识库的检索结果。
4. 图片风险标签为空或通过允许规则。
5. 图片本地文件真实存在。
6. 图片目标商品与当前对话焦点一致，避免客户问 K87 却回复 K68 图片。

如果机器人不允许自动发图：

- 只展示 AI 文字回复。
- 图片候选仍可记录到 trace 和文字回复 metadata，方便分析。
- 不保存 `assistant/image` 沙盒消息。

### 8.2 消息顺序

沙盒应模拟真实自动回复链路的发送顺序：

```text
assistant / text
assistant / image
```

例如：

```text
AI 文字气泡：亲，这是 K87 黑红配色的正面实拍图，您可以看下整体布局哦~
AI 图片气泡：keyboard_k87_inphic_black_red_front.png
```

### 8.3 图片气泡

图片气泡建议支持：

- 图片缩略图。
- 图片标题或文件名。
- 点击预览原图。
- tooltip 展示匹配理由、匹配分数和风险标签。
- 图片文件不存在时不展示，并记录 `image_file_missing`。

首版每轮 AI 回复最多展示 1 张图片，和当前真实自动回复链路保持一致，避免一次返回过多相似素材。

## 10. DAO 与服务建议

### 10.1 DAO

建议新增：

```text
RobotSandboxMessageDao
```

核心方法：

```cpp
QVector<RobotSandboxMessageRecord> listRecent(const QString& robotId, int limit) const;
bool append(const RobotSandboxMessageRecord& message);
bool appendMany(const QVector<RobotSandboxMessageRecord>& messages);
bool clearForRobot(const QString& robotId);
```

记录结构：

```cpp
struct RobotSandboxMessageRecord {
    qint64 id = 0;
    QString robotId;
    QString role;
    QString content;
    QString contentType = "text";
    QString imagePath;
    QJsonObject metadata;
    QString createdAt;
};
```

### 10.2 构建服务

建议在 `AiChatAppService` 中增加沙盒构建方法，或抽出更通用的构建输入：

```cpp
AggregateAiBuiltRequest buildRobotSandboxReplyRequest(
    const RobotRuntimeConfig& robotConfig,
    const QVector<RobotSandboxMessageRecord>& recentMessages,
    const QString& latestUserText,
    const QList<KnowledgeSnippetContext>& knowledgeSnippets,
    const AggregateReplyStrategy& strategy
) const;
```

如果为了首版快速落地，也可以先新增专用方法，后续再抽象统一。

## 11. UI 实现建议

### 11.1 对话框类

建议新增：

```text
RobotSandboxDialog
```

或放在后台窗口 cpp 中先做内部类，稳定后再拆文件。

主要成员：

```cpp
QString m_robotId;
QJsonObject m_robot;
QScrollArea* m_chatScroll;
QVBoxLayout* m_messageLayout;
QPlainTextEdit* m_inputEdit;
QPushButton* m_clearButton;
QPushButton* m_sendButton;
IAiStreamingSession* m_session;
QString m_accumulated;
QList<AggregateImageCandidate> m_imageCandidates;
```

### 11.2 气泡布局

可以先复用聚合界面视觉思路，不强行复用复杂 delegate。

首版建议用普通 QWidget 气泡：

```text
user:
  row align right
  bubble background #2563eb
  text color white

assistant:
  row align left
  bubble background #ffffff
  border #e2e8f0
  text color #0f172a

assistant image:
  row align left
  image thumbnail
  title/file name below image
  click to preview
```

这样开发成本低，视觉上也足够像聊天窗口。

### 11.3 发送状态

发送后：

- 禁用发送按钮。
- 输入框可暂时禁用或保持可编辑。
- 聊天区追加用户气泡。
- 追加一个临时 AI 气泡：“AI 正在回复...”
- 流式输出时更新该气泡。
- 完成后保存 assistant 文本消息。
- 如果机器人允许自动发图并命中安全图片，在文本消息后保存并展示 assistant 图片消息。
- 失败时显示错误并恢复按钮。

## 12. 分阶段落地

### 阶段一：基础沙盒

- 机器人列表操作列新增“测试回复”按钮。
- 新增 `RobotSandboxDialog`。
- 新增 `robot_sandbox_messages` 表和 DAO。
- 支持按机器人加载测试历史。
- 支持清空当前机器人测试历史。
- 支持发送文本问题。
- 支持 AI 文本回复展示和保存。
- 测试用户暂不支持图片发送。
- 机器人开启 `allow_auto_send_images` 时，支持 AI 回复一张知识库图片素材。
- AI 图片以独立 `assistant/image` 沙盒消息保存，文字在前、图片在后。
- 图片消息支持缩略图和点击预览。
- 使用机器人模型、知识库、语气和称呼策略。

### 阶段二：链路增强

- 沙盒 trace 记录完整 Prompt、检索 query、知识库命中和模型回复。
- 支持展示图片素材候选、匹配理由和风险标签。
- 支持多条消息拆分、截断和去重展示。
- 支持短确认场景按沙盒历史判断是否继续检索。

### 阶段三：体验增强

- 展示机器人当前配置摘要。
- 展示知识库命中片段。
- 支持查看未发送的图片候选。
- 支持复制 AI 回复。
- 支持重新生成上一条回复。
- 支持清空前二次确认。

### 阶段四：测试集与回归

- 支持保存常用测试问题。
- 支持一键跑一组测试问题。
- 支持对比不同机器人回复。
- 支持人工标注“好 / 一般 / 差”。
- 支持导出测试结果。

## 13. 风险与注意事项

- 沙盒不要写真实客户消息表，避免污染真实接待。
- 沙盒不要触发真实平台发送。
- 沙盒调用模型仍可能消耗接口额度，需要明确按钮状态和错误提示。
- 如果机器人绑定的知识库已删除或停用，应在沙盒顶部提示。
- 如果机器人模型配置缺失，应阻断发送。
- 如果 Python 服务未启动，应允许无知识库测试模型回复，或明确提示“知识库不可用，将只按上下文生成”。
- 沙盒多轮历史只对当前机器人生效，不应跨机器人共享。
- AI 图片回复只能使用知识库中已存在且通过风险校验的图片，不应调用模型临时生成图片。
- 沙盒中的 AI 图片消息只用于展示测试效果，不触发任何真实平台发送。

## 14. 推荐结论

推荐按“机器人独立沙盒会话”实现，而不是只做单次输入输出测试框。

原因：

- 更接近真实客服对话。
- 可以测试多轮追问、短确认、上下文指代和多条消息策略。
- 每个机器人有自己的测试历史，方便围绕具体机器人持续调试。
- 不污染真实客户会话，也不触发真实平台发送。
- 后续可以自然扩展为测试集、回归测试和机器人效果评估工具。

### 15.2 阶段二：链路增强

阶段二已补充以下能力：

- 沙盒每次测试回复调用会写入独立 trace 日志，路径为 `python/rpa/logs/robot_sandbox/robot_sandbox_trace_yyyyMMdd.log`。
- trace start 记录机器人 ID、机器人名称、模型配置、绑定知识库、客户最新问题、知识库检索 query、知识库命中片段、图片候选和最终给大模型的完整请求。
- trace finish 记录模型原始输出、拆分后的最终消息、拆分/截断/去重状态、选中的附图和失败原因。
- 图片素材检索后，会在沙盒界面状态区下方展示候选摘要，包括候选图标题、分数、是否建议附图、风险标签和匹配理由。
- 图片素材未检索、未绑定知识库、Python 服务不可用、未命中或机器人未开启发图时，会在候选摘要或状态文案里给出原因。
- 多条消息仍使用 `---MSG---` 分隔，按机器人 `max_auto_send_messages` 截断，并对高度相似内容做去重。
- 多条消息拆分结果会写入 trace 的 `split_status`，用于判断原始输出条数、最终展示条数、去重数和截断数。
- 短确认场景继续沿用阶段一策略：如果客户只回复“好 / 可以 / ok”等，会优先查看上一条 AI 文本是否期待继续；若期待继续，则使用上一条 AI 消息补全知识库检索 query，否则跳过检索并只结合沙盒上下文生成。

当前阶段仍不做测试集、批量回归、复制回复、重新生成等体验增强能力，这些归入后续阶段。

### 15.3 图片知识与文档知识一致性优化

针对“客户明确索要某个物品实拍图，但文档命中和图片命中不一致”的问题，已补充以下策略：

- Excel 文档导入时按行保留空块，一条快捷短语行会优先形成独立 chunk，避免多行内容被拼成超长 chunk 后在 Prompt 中截断。
- 相邻 chunk 合并时，如果命中内容是 Excel 的 `第 N 行：` 格式，则不再合并前后行，避免把无关快捷短语带进同一个片段。
- 知识库目录导入图片时改为递归扫描，`image/` 子目录下的素材也会被导入图片素材库。
- 图片素材检索支持按 `original_filename` / title 精确命中；当 query 中包含 `quick_phrase_r033_拔键器.jpg` 这类文件名时，会优先返回对应图片。
- 机器人沙盒会从知识片段中提取 `图片名=...`，客户索要图片且文档片段已关联图片名时，优先用该图片名检索图片素材。
- 如果知识片段关联了图片名但图片素材库找不到对应文件，沙盒状态与 trace 会提示需要重建或导入图片目录，不再回退到宽泛图片检索误发无关图。
- 图片候选增加对象一致性过滤：客户明确问“拔键器”时，候选标题、原始文件名或路径必须包含“拔键器”，否则不附图。
- 聚合主链路也增加了非型号物品的图片焦点识别，除 K87/K98/K68 这类型号外，也支持“拔键器”等明确物品名过滤。
- 如果模型文字已经表达“没有/暂无实拍图/需要核实”，客户端会阻止附图，避免出现文字说没有图但实际又发送图片的矛盾。
- Prompt 规则补充：当知识片段出现 `是否有图=是` 或 `图片名=...` 时，模型不应回答“没有图片/暂无实拍图”。

注意：以上导入与切分策略需要对对应知识库执行“重新导入/重建”后，已有 Excel 文档和图片素材才能按新规则重新入库。
