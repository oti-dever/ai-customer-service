# 小型自研知识库服务实现方案

日期：2026-06-30

## 1. 背景

RAGFlow 适合作为完整知识库平台，但对当前 PoC 来说部署成本偏高：本机需要 Docker Desktop 和接近 16GB 可用内存，云服务器也建议至少 4 核 16GB 100GB。当前项目的真实诉求更窄：在 AI 草稿生成前，从少量店铺/商品文档中检索可靠原文片段，并注入现有 prompt。

如果第一阶段文档数量不多、格式可控、权限模型简单，可以先自研一个小型知识库服务。它不尝试复刻 RAGFlow，而是只实现当前客服回复链路需要的核心能力：

```text
导入文档
  -> 抽取文本
  -> 切分 chunk
  -> 建立轻量索引
  -> 根据客户问题检索 topK 原文片段
  -> 注入现有 AI 草稿生成 prompt
```

本方案是 RAGFlow PoC 的轻量替代路线。后续如果文档规模、解析复杂度、OCR、权限、多租户或运维要求上升，仍可切换到 RAGFlow、Qdrant、Chroma 或其他知识库服务。

## 2. 设计目标

### 2.1 要解决的问题

1. 当前 AI 草稿缺少业务知识依据，容易编造商品、售后、发货、价格和活动规则。
2. 外部完整 RAG 平台部署成本偏高，P0 阶段需要更轻的验证路径。
3. 客服回复链路只需要检索“可引用原文片段”，不需要完整知识库平台能力。
4. 需要保留后续替换为 RAGFlow 或向量数据库的空间。

### 2.2 首版目标

首版只做“小而完整”的闭环：

- 支持知识库和文档管理。
- 支持 `txt`、`md`、`docx`、`pdf` 文本抽取。
- 支持文档切片、入库、删除、重建索引。
- 支持关键词检索和基础向量检索二选一或组合。
- 提供统一 `/knowledge/search` 接口。
- 返回原文片段、来源、分数和文档元数据。
- AI 草稿生成失败时可降级到无知识库链路。

## 3. 非目标

首版明确不做：

- 不做扫描件 OCR。
- 不做网页抓取。
- 不做在线文档编辑器。
- 不做复杂多租户权限体系。
- 不做知识图谱。
- 不做完整后台 CMS。
- 不做重排模型服务。
- 不做大规模分布式向量库。
- 不把最终 AI 回复生成迁移到知识库服务。

这些能力等需求真实出现后再升级。

## 4. 总体架构

推荐把小型知识库作为 Python sidecar 的一个独立模块，或作为同机独立 Python 服务启动。首版更建议放在 Python 服务侧，因为文档解析、embedding 和 SQLite 生态都更成熟。

```text
后台知识库管理 UI
  -> C++ IPC / HTTP
  -> Python Knowledge Service
  -> SQLite + 文档文件目录

聚合会话 AI 草稿生成
  -> C++ 取最近会话上下文
  -> KnowledgeRetrievalClient 调 /knowledge/search
  -> Python Knowledge Service 检索 topK chunk
  -> C++ 注入 AiRequest.systemPrompt
  -> 现有 AiServiceFacade / IAiStreamingSession 流式生成
```

边界：

- C++ 负责 UI、AI 配置、prompt 注入和流式生成。
- Python 知识库服务负责文档解析、切片、索引和检索。
- SQLite 是本地事实源。
- 文档原文件保存在工作区或用户数据目录。
- 向量库首版不单独部署，避免引入额外服务。

## 5. 分阶段路线

### V0：关键词检索版

V0 不做 embedding，只做确定性关键词检索。

能力：

- 文档上传/删除。
- 文本抽取。
- chunk 切分。
- SQLite 存储。
- FTS5 全文检索或轻量 BM25。
- 返回 topK chunk。

优点：

- 实现快。
- 不依赖模型。
- 资源占用低。
- 适合 SKU、型号、政策名、活动名、明确关键词问题。

缺点：

- 同义词、口语化、省略表达效果一般。
- 对“尺码不合适能不能退”这类语义问题，可能不如向量检索。

### V1：向量检索版

V1 增加 embedding。

能力：

- chunk 入库时生成 embedding。
- query 时生成 embedding。
- 用 numpy 或纯 Python 计算余弦相似度。
- topK 结果按相似度排序。
- 可叠加关键词分数。

小规模时不需要向量数据库。几千到几万个 chunk 以内，SQLite 取出 embedding 后做内存排序即可满足 PoC。

### V2：混合检索增强版

当前 V1 实现已经支持 `keyword/vector/hybrid` 三种模式，默认 `hybrid` 会按 `0.6 * vector_score + 0.4 * keyword_score` 做基础融合。因此 V2 不再定义为“从零新增混合检索”，而是把现有 hybrid 升级成更稳定、更可解释、更贴近客服场景的检索排序系统。

V2 增强目标：

```text
query
  -> 提取型号、规格、场景类关键词
  -> FTS/BM25 关键词打分
  -> embedding 向量相似度打分
  -> 标题、型号、图片标签、OCR、适用场景等字段权重加成
  -> 根据 query 类型动态调整关键词/向量权重
  -> 分数归一化并融合排序
  -> 返回 topK
```

首版增强综合分仍保持简单可解释：

```text
final_score = vector_weight * vector_score + keyword_weight * keyword_score + metadata_boost
```

权重建议：

- 默认问题：`vector_weight=0.6`，`keyword_weight=0.4`。
- 明确型号、规格、颜色、尺寸、实拍等问题：提高关键词和字段命中权重，避免 K87/K98/K68 串货。
- 口语化售后、物流、发货、保修等问题：保持向量权重更高，提升自然语言召回。

实施优先级：

1. 使用 SQLite FTS5/BM25 增强关键词侧排序，保留现有 `_keyword_score()` 作为兜底。
2. 增加商品型号、标题、图片素材 `tags/scenarios/ocr_text` 等字段权重。
3. 根据 query 类型动态调整向量分和关键词分的融合权重。
4. 文本知识库结果支持相邻 chunk 合并：排序仍以命中的核心 chunk 为准，输出给大模型的 `snippet` 可向前/向后各合并 1 个相邻 chunk，总长度控制在约 1600 字符内，避免答案跨 chunk 时上下文不完整。
5. 后续再考虑二阶段 rerank。

### V3：外部向量库/完整 RAG 平台

当出现以下情况时再升级：

- chunk 数量超过十万级。
- 检索延迟不可接受。
- 需要多机部署。
- 需要复杂元数据过滤。
- 需要 OCR、复杂表格解析、版面解析。
- 需要完整可视化知识库平台。

升级方向：

- SQLite + 内存向量检索 -> Qdrant / Chroma / FAISS。
- 自研文档解析 -> RAGFlow 文档解析。
- 自研服务接口保持 `/knowledge/search` 不变。

## 6. 技术选型

### 6.1 服务层

推荐：

- Python FastAPI 或当前 Python sidecar 内置 HTTP 路由。
- 如果想减少新依赖，首版可先用当前服务框架；如果已有 Flask/FastAPI，则复用。

不建议：

- C++ 侧直接解析文档和做 embedding。
- 把知识库逻辑写进 UI 层。

### 6.2 存储

推荐 SQLite：

- 轻量。
- 易备份。
- 当前项目已有 SQLite 使用经验。
- 可开启 FTS5 做全文检索。

存储内容：

- 知识库元数据。
- 文档元数据。
- chunk 文本。
- FTS 索引。
- embedding 二进制或 JSON。
- 检索日志。

### 6.3 文本抽取

建议：

| 格式 | 首版实现 |
|---|---|
| `.txt` | UTF-8/GBK 探测后读取 |
| `.md` | 读取 Markdown 原文，保留标题 |
| `.docx` | `python-docx` 抽取段落和表格 |
| `.pdf` | `pypdf` 或 `pdfplumber` 抽取文本 |
| `.xlsx` / `.xlsm` | `openpyxl` 按工作表识别表头行，并将每行转成“字段名=字段值”的结构化文本 |

首版不做 OCR。扫描 PDF 或图片文档直接标记为 `failed`，提示用户转换为可复制文本的 PDF/Word/TXT。

### 6.4 embedding

两个方案：

1. 外部 embedding API。
   - 接入快。
   - 成本按量。
   - 不占本机内存。

2. 本地 embedding 模型。
   - 适合离线和隐私场景。
   - 推荐后续再做。
   - 需要评估模型加载内存。

PoC 建议优先外部 embedding API，或者 V0 先不做 embedding。

### 7.1 knowledge_bases

```sql
CREATE TABLE knowledge_bases (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT NOT NULL DEFAULT '',
    enabled INTEGER NOT NULL DEFAULT 1,
    platform TEXT NOT NULL DEFAULT '',
    shop_id TEXT NOT NULL DEFAULT '',
    robot_id TEXT NOT NULL DEFAULT '',
    scene TEXT NOT NULL DEFAULT 'reply_draft',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

### 7.2 knowledge_documents

```sql
CREATE TABLE knowledge_documents (
    id TEXT PRIMARY KEY,
    base_id TEXT NOT NULL,
    title TEXT NOT NULL,
    original_filename TEXT NOT NULL,
    file_path TEXT NOT NULL,
    file_type TEXT NOT NULL,
    file_size INTEGER NOT NULL DEFAULT 0,
    content_hash TEXT NOT NULL,
    status TEXT NOT NULL,
    enabled INTEGER NOT NULL DEFAULT 1,
    version INTEGER NOT NULL DEFAULT 1,
    error_message TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

文档状态：

```text
uploaded
extracting
chunking
indexing
ready
failed
disabled
deleted
```

### 7.3 knowledge_chunks

```sql
CREATE TABLE knowledge_chunks (
    id TEXT PRIMARY KEY,
    base_id TEXT NOT NULL,
    document_id TEXT NOT NULL,
    chunk_index INTEGER NOT NULL,
    title_path TEXT NOT NULL DEFAULT '',
    content TEXT NOT NULL,
    token_estimate INTEGER NOT NULL DEFAULT 0,
    content_hash TEXT NOT NULL,
    embedding BLOB,
    enabled INTEGER NOT NULL DEFAULT 1,
    created_at TEXT NOT NULL,
    updated_at TEXT NOT NULL
);
```

### 7.4 FTS 表

```sql
CREATE VIRTUAL TABLE knowledge_chunks_fts USING fts5(
    content,
    title_path,
    content='knowledge_chunks',
    content_rowid='rowid'
);
```

如果 SQLite rowid 映射不方便，也可以维护独立 FTS 表：

```sql
CREATE VIRTUAL TABLE knowledge_chunks_fts USING fts5(
    chunk_id UNINDEXED,
    base_id UNINDEXED,
    document_id UNINDEXED,
    title_path,
    content
);
```

首版实现以后者更简单。

### 7.5 retrieval_events

```sql
CREATE TABLE knowledge_retrieval_events (
    id TEXT PRIMARY KEY,
    query TEXT NOT NULL,
    platform TEXT NOT NULL DEFAULT '',
    shop_id TEXT NOT NULL DEFAULT '',
    scene TEXT NOT NULL DEFAULT '',
    result_count INTEGER NOT NULL DEFAULT 0,
    latency_ms INTEGER NOT NULL DEFAULT 0,
    mode TEXT NOT NULL DEFAULT '',
    created_at TEXT NOT NULL
);
```

用于调试检索效果和后续评估命中率。

## 8. 文档处理流程

### 8.1 上传/导入

```text
POST /knowledge/documents
  -> 保存原文件
  -> 写 knowledge_documents(status=uploaded)
  -> 异步或同步进入 parse pipeline
```

PoC 可先同步处理，文档少时体验可接受。正式 UI 再改成异步。

### 8.2 文本抽取

```text
uploaded
  -> extracting
  -> extract text
  -> failed 或 chunking
```

抽取原则：

- 保留标题层级。
- 表格按行转成文本。
- 页眉页脚可忽略。
- 空白、重复换行、不可见字符要清理。
- 抽取文本为空则失败。

### 8.3 chunk 切分

首版切分策略：

- 优先按 Markdown/Word 标题切。
- 标题下内容过长时按段落继续切。
- 单个 chunk 建议 300 到 800 中文字。
- 相邻 chunk 可保留 50 到 100 字重叠。
- chunk 中保留 `title_path`，便于返回来源。

示例：

```text
title_path: 机械键盘售后与保修政策 > 7 天内质量问题处理
content: 客户签收后 7 天内，如键盘出现非人为质量问题...
```

### 8.4 索引

V0：

- chunk 写入 SQLite。
- chunk 写入 FTS5。

V1：

- 在 V0 基础上生成 embedding。
- embedding 存 BLOB。
- embedding 生成失败时文档可仍保持关键词检索可用，但状态标记 `ready_partial` 或记录 warning。

## 9. 检索流程

### 9.1 请求

```http
POST /knowledge/search
```

```json
{
  "query": "客户最新问题",
  "conversation_history": [
    {"role": "customer", "content": "这个可以退吗"},
    {"role": "agent", "content": "请问您收到货了吗"}
  ],
  "platform": "qianniu",
  "shop_id": "keyboard-demo-shop",
  "robot_id": "robot-keyboard-service",
  "scene": "reply_draft",
  "base_ids": ["kb-after-sale"],
  "top_k": 5,
  "mode": "hybrid"
}
```

### 9.2 查询改写

首版不调用大模型做 query rewrite，只做规则拼接：

```text
客户最新问题 + 最近 2 到 4 条上下文摘要
```

例如：

```text
场景：电商客服回复草稿。
客户最新问题：键盘一个键不触发，可以换吗？
最近上下文：客户刚收到三天，询问售后处理。
```

### 9.3 关键词检索

V0 使用 FTS5：

- 对 query 做简单分词或字符 n-gram。
- 命中标题加权。
- 命中当前 `base_id/shop_id/scene/enabled` 范围。
- 取 top 20 候选。

如果中文 FTS 分词效果不理想，可先做简单 fallback：

- 提取关键词。
- 对 chunk content 做包含匹配。
- 按命中数量和关键词长度打分。

### 9.4 向量检索

V1：

- query 生成 embedding。
- 读取候选范围内 chunk embeddings。
- 计算余弦相似度。
- 返回 top 20 候选。

embedding BLOB 建议存 `float32` 数组：

```text
bytes = numpy.asarray(vector, dtype=float32).tobytes()
```

### 9.5 结果合并

合并逻辑：

- 按 `chunk_id` 去重。
- 同一文档连续 chunk 可合并，但首版可先不做。
- 过滤过短、低分、disabled chunk。
- 每个文档最多返回 2 个 chunk，避免一个文档占满全部结果。

返回 topK：

```json
{
  "status": "success",
  "results": [
    {
      "source_id": "doc-001",
      "chunk_id": "chunk-008",
      "source_title": "机械键盘售后与保修政策.docx",
      "title_path": "7 天内质量问题处理",
      "snippet": "客户签收后 7 天内，如键盘出现非人为质量问题...",
      "score": 0.86,
      "match_type": "hybrid",
      "metadata": {
        "base_id": "kb-after-sale",
        "shop_id": "keyboard-demo-shop"
      }
    }
  ],
  "metadata": {
    "mode": "hybrid",
    "latency_ms": 42
  }
}
```

## 10. Prompt 注入

保持和既有知识库方案一致，由 C++ 侧注入：

```text
【知识库检索结果】
以下内容是从店铺知识库检索到的原文片段。涉及商品、售后、物流、价格、活动、发票等事实问题时，必须优先依据这些片段回答。没有覆盖的信息不要编造承诺。

1. 来源：机械键盘售后与保修政策.docx
原文：客户签收后 7 天内，如键盘出现非人为质量问题，可根据问题程度安排换新、补发配件、维修或退货。

要求：
- 回复客户时不要暴露 chunk_id、score、base_id 等内部字段。
- 如果知识库片段不足以确认结论，请引导客户补充信息或说明需要进一步核实。
- 不要输出“根据知识库”这类生硬表述。
```

注入控制：

- top 3 到 top 5。
- 每个 chunk 300 到 500 字。
- 总知识库上下文 1500 到 2500 字。
- 低分结果不注入。

### 10.1 客服视角的最终提示词结构

最终给大模型的提示词不应只做“聊天记录 + 知识库片段”的简单拼接，而应从客服接待视角组织任务，让模型先理解当前应该回复什么，再决定是否使用知识库。

推荐整体结构：

```text
system prompt
  -> 客服角色和回复目标
  -> 最新消息优先原则
  -> 最近 10 条聊天记录的使用边界
  -> 场景判断和回复策略
  -> 知识库使用规则
  -> 输出格式和语气要求

knowledge block，可选
  -> 店铺知识库检索结果 topK 原文片段
  -> 事实边界和禁止暴露内部字段

conversation history
  -> 最近 10 条消息，包含客户消息和我方消息
  -> 仅作为上下文参考

user turn
  -> 客户最新入站
  -> 明确要求重点回应最新入站，历史只辅助参考
```

核心原则：

- `客户最新入站` 是主任务。
- 最近 10 条聊天记录只用于理解上下文、称呼、订单背景、客户偏好、是否已经回答过，不能把历史问题重新回答一遍。
- 如果客户最新消息是追问，只回答追问点。
- 如果客户最新消息换了话题，不要把旧话题再次展开。
- 如果历史里已经明确回复过某个问题，本轮不要重复完整回答。
- 知识库只提供事实依据，最终回复仍要改写成自然客服口吻。

推荐 system prompt 内容：

```text
你是电商店铺客服场景的辅助起草助手。请起草一条可直接发送给客户的回复正文。

任务优先级：
1. 必须优先回应【客户最新入站】中的最后一条消息。
2. 最近聊天记录只作为理解上下文、称呼、订单背景、客户偏好和避免重复追问的参考，不要喧宾夺主。
3. 不要把历史里已经回答过的问题重新回答一遍。
4. 如果客户最新消息只是商品链接、商品卡片、商品ID，且没有明确咨询问题，请按新客户/浏览商品场景接待。

场景处理：
- 仅商品链接/商品卡片/商品ID：亲切欢迎，询问客户想了解规格、价格、发货、售后还是其他问题；可以简短介绍店铺主营品类；不要编造该商品的具体规格、库存、价格或活动。
- 明确咨询商品问题：直接回答最新问题，必要时结合聊天记录和知识库。
- 追问上一轮问题：只回答追问点，不重复上一轮完整答案。
- 信息不足：只问一个最关键的补充问题，不要连续追问多个问题。
- 售后、物流、价格、活动、发票等事实问题：优先依据知识库片段和聊天上下文；知识库没有覆盖时，不要编造承诺，可说明需要进一步核实。
- 情绪、催促、投诉：先安抚，再给出当前能做的处理或需要补充的信息。

输出要求：
只输出可直接发送给客户的纯文本正文。
不要 Markdown、标题、表格、项目符号、代码块。
不要加“客服：”等前缀，不要用引号包裹整段回复。
语气亲切、温和、不失热情，可自然使用“亲”“宝子”等称呼，但不要堆砌。
默认简短，通常 1 到 3 句话即可；只有客户明确要求详细说明时才适当展开。
```

商品卡片场景示例：

```text
客户最新入站：
商品ID：970947366369复制
```

如果当前只解析到了商品 ID，没有商品标题、价格、规格等完整信息，推荐回复方向：

```text
亲，看到您发的商品啦～您是想了解这款的规格、价格、发货还是售后问题呢？我们店里主要有键盘、键帽和相关配件，您也可以直接把想了解的点发我，我帮您看。
```

注意：

- 如果消息采集层后续能解析商品卡片标题、价格、规格按钮或商品链接，应把这些字段作为结构化上下文传给模型。
- 仅商品 ID 不足以确认具体商品详情，不应让模型硬编商品参数。
- 此类新客户/商品卡片消息可以不强行检索知识库；如果能拿到商品标题或 SKU，再用标题/SKU 作为检索 query。

## 11. 管理接口

当前 Python sidecar 已经提供一组 `/api/knowledge/...` 接口，能支撑 PoC 阶段的导入、文档列表、图片素材列表和检索。后续如果要把后台“产品知识库”升级为“知识库配置 + 平台绑定”的管理模型，需要在现有接口上补一批管理能力。

接口设计原则：

- C++ 聚合界面和后台 UI 只调用 Python sidecar，不直接访问 SQLite。
- 检索接口继续保持稳定，管理接口负责维护 `base_id`、目录、启用状态和平台绑定。
- 平台绑定只影响检索时传入的 `base_ids`，不改 Prompt 注入和大模型调用链路。
- “适用店铺”只做人工说明，不作为检索硬过滤条件。

## 13. 性能预估

小规模假设：

- 文档数：10 到 200。
- chunk 数：500 到 20000。
- 单 chunk：300 到 800 中文字。
- embedding 维度：384 到 1024。

资源预估：

- SQLite 文本和元数据：几十 MB 到几百 MB。
- embedding：`chunk_count * dim * 4 bytes`。
- 10000 chunks、768 维约 29MB。
- 检索时全量载入 embedding 做余弦相似度，本机可接受。

因此在当前开发机和轻量云服务器上，自研小型知识库都比 RAGFlow 更容易跑起来。

## 14. 风险和约束

1. 自研解析能力弱于 RAGFlow，复杂 PDF、扫描件、表格效果有限。
2. 中文分词和 FTS5 效果可能不稳定，需要针对客服文档做规则补偿。
3. 向量检索质量依赖 embedding 模型。
4. 文档替换、删除和重建索引要保证一致性，避免旧 chunk 继续命中。
5. 小型服务只能解决当前 PoC，不应无限扩展成复杂平台。

## 15. 验收标准

以 `docs/knowledge-base` 键盘/键帽测试资料为初始验证集。

通过标准：

- 4 份测试文档可导入。
- 文档状态可进入 `ready`。
- chunk 数量合理，不出现整篇文档一个 chunk 或每句话一个 chunk。
- 10 个测试问题中，大部分能命中正确文档片段。
- 搜索接口耗时可接受，目标小于 500ms；使用外部 embedding 时另行评估。
- 知识库服务失败时，AI 草稿生成能降级为无知识库模式。

## 16. 实施建议

建议先做 V0，再做 V1：

1. V0 关键词检索：快速打通文档导入、chunk、SQLite、search API、prompt 注入。
2. V1 向量检索：接入 embedding，提升自然语言问题的召回。
3. V2 混合检索：关键词 + 向量融合排序。
4. V3 外部化：当数据规模和复杂度上升时切换 Qdrant/RAGFlow。

关键原则：接口先稳定，内部实现可替换。

### 17.1 本阶段目标


- 检索失败、超时或无结果时，自动降级为当前无知识库生成链路。

### 17.3 Prompt 注入规则

注入位置：`AiChatAppService::buildAggregateReplyRequest()` 生成的 system prompt。

推荐格式：

```text
【店铺知识库检索结果】
以下内容是从店铺知识库检索到的原文片段。涉及商品、售后、物流、价格、活动、发票等事实问题时，必须优先依据这些片段回答。没有覆盖的信息不要编造承诺。
```

- 每个片段最多 500 字。
- 总知识库上下文控制在 2000 字以内。
- 低分或空片段不注入。

## 18. V1 向量检索实施记录

日期：2026-07-01

V1 在 V0 已打通导入、文档列表、关键词检索和 Prompt 注入的基础上，先实现一个无外部依赖、无付费 API 的本地 embedding 基线，用于验证向量检索链路本身是否可用。

### 18.1 本阶段目标

```text
文档导入/重建
  -> chunk 文本生成本地 embedding
  -> embedding 以 BLOB 写入 SQLite
  -> 搜索请求生成 query embedding
  -> SQLite 读取候选 chunk embedding
  -> 内存计算余弦相似度
  -> 返回 vector/hybrid 结果
```

### 18.2 当前实现选择

- 不引入 Qdrant、Chroma、FAISS 等外部向量库。
- 不调用外部 embedding API，避免开发阶段产生额外成本和密钥配置。
- 使用本地字符 n-gram/词项特征哈希生成固定维度向量，模型标识为 `local-hash-ngram-v1`。
- embedding 维度先固定为 `384`，以 `float32` 小端 BLOB 存入 `knowledge_chunks.embedding`。
- 搜索接口支持 `mode=keyword/vector/hybrid`。
- 老调用不传 `mode` 时默认走 `hybrid`，让聚合界面可以直接吃到 V1 能力。
- hybrid 模式下向量分和关键词分融合排序，关键词仍作为保底。

### 18.3 重要边界

`local-hash-ngram-v1` 是本地 PoC 基线，不等同于真正语义 embedding 模型。它的价值主要是先稳定以下工程链路：

- embedding 字段迁移。
- chunk 入库时写向量。
- query 时生成向量。
- 向量相似度排序。
- 搜索结果携带 `match_type`、`keyword_score`、`vector_score`。

后续如果要提升“同义词、口语化、省略表达”的召回质量，可以在不改 HTTP 接口和 C++ 调用链路的情况下，将 `local-hash-ngram-v1` 替换为：

- 外部 embedding API。
- 本地轻量 embedding 模型。
- 独立向量库或 RAG 平台。

### 18.4 验收方式

1. 重启 Python 服务，让 schema 自动补齐 embedding 字段。
2. 在后台重新导入/重建 `docs/knowledge-base`。
3. 调 `/api/knowledge/search`，不传 `mode` 时应返回 `metadata.mode=hybrid`。
4. 显式传 `mode=vector` 时，命中结果的 `match_type` 应为 `vector`，metadata 中应包含 `vector_score`。
5. 聚合界面点击“生成本条回复”时，仍走同一个 `/api/knowledge/search`，检索结果继续注入 Prompt。

### 18.5 BGE 语义 embedding 接入

在本地哈希 embedding 基线稳定后，V1 进一步接入 `BAAI/bge-small-zh-v1.5` 作为默认语义 embedding 模型。

实现方式：

- Python 服务默认尝试加载 `BAAI/bge-small-zh-v1.5`。
- 使用 `sentence-transformers` 本地加载模型并在 CPU 上推理。
- query embedding 会追加 BGE 中文检索 instruction：`为这个句子生成表示以用于检索相关文章：`。
- chunk embedding 不追加 query instruction，直接使用标题、标题路径和正文组合文本。
- 模型不可用、依赖未安装或加载失败时，自动回退到 `local-hash-ngram-v1`。
- 搜索时按 chunk 自己的 `embedding_model` 生成对应 query embedding，因此旧 local 向量和新 BGE 向量可以共存。

运行依赖：

```text
python/service/requirements-knowledge-embedding.txt
```

配置项：

```text
AI_CUSTOMER_SERVICE_EMBEDDING_MODEL=BAAI/bge-small-zh-v1.5
AI_CUSTOMER_SERVICE_EMBEDDING_DEVICE=cpu
AI_CUSTOMER_SERVICE_EMBEDDING_CACHE_DIR=可选，本地模型缓存目录
AI_CUSTOMER_SERVICE_EMBEDDING_ALLOW_DOWNLOAD=1 时允许业务进程联网下载模型；默认不允许，避免导入时长时间卡住
```

推荐把模型提前下载到项目目录：

```powershell
$env:HF_ENDPOINT="https://hf-mirror.com"
hf download BAAI/bge-small-zh-v1.5 --local-dir database\models\bge-small-zh-v1.5
```

如果 `database/models/bge-small-zh-v1.5/modules.json` 存在，Python 服务会自动优先从该本地目录加载 BGE，并在数据库中统一记录模型标识为 `BAAI/bge-small-zh-v1.5`。

如果需要临时回退本地哈希 embedding：

```text
AI_CUSTOMER_SERVICE_EMBEDDING_MODEL=local-hash-ngram-v1
```

注意：切换到 BGE 后，已有文档需要重新导入/重建，新的 chunk 才会写入 BGE embedding。未重建前，旧 local embedding 仍可被 hybrid 检索兼容使用。

## 19. 图片知识库/素材库扩展方向

在文本知识库已经能支撑“生成本条回复”的基础上，后续可以把客服常用图片也纳入知识库体系，形成“图片知识库/素材库”。这里的重点不是自动回复链路能不能发送图片，而是系统必须先知道每张图片是什么、适合什么场景、什么时候不能发。

### 19.1 设计目标

图片素材库解决以下问题：

1. 客服常用图片分散在本地目录、聊天记录或临时文件中，缺少统一管理。
2. 自动回复即使支持发图，也无法判断“应该发哪张图”。
3. 图片可能包含商品实拍、规格尺寸、安装说明、售后说明、活动价格、平台水印或隐私信息，需要先做风险识别。
4. 客户发来的问题有时更适合用图片辅助回答，例如“有实拍图吗”“尺寸图发一下”“怎么安装”“这个颜色是什么样”。

首版目标不是让 AI 自动发图，而是先做到：

```text
导入图片目录
  -> 多模态模型分析图片内容
  -> 生成摘要、OCR 文本、标签、适用场景、风险标签
  -> 入库
  -> 客户咨询时检索候选图片
  -> AI 生成文字回复时给出“建议附图”
  -> 客服人工确认后发送
```

### 19.2 图片入库信息

图片不能只保存文件路径，建议至少保存以下元数据：

- 原图路径、缩略图路径、文件名、文件大小、图片 hash。
- 图片类型：商品图、实拍图、规格图、尺寸图、安装说明、售后说明、物流说明、活动图、纯文本图、其他。
- 图片内容摘要：由豆包等多模态模型分析生成，用自然语言描述图片主要内容。
- 图片 OCR 文本：如果图片中有文字，需要抽取出来，用于后续关键词/语义检索。
- 适用场景：例如材质咨询、尺寸咨询、配列咨询、颜色咨询、安装咨询、售后咨询、物流咨询。
- 关联商品或类目：例如键盘、键帽、轴体、数据线、配件，后续可扩展 SKU/商品 ID。
- 风险标签：含价格、含活动、含过期信息、含平台水印、含隐私信息、不建议自动发送。
- 推荐话术：例如“亲，这张图可以参考下，是这款键帽的实拍效果”。
- 状态：ready、needs_review、disabled、error。

### 19.3 多模态分析方式

导入图片时可以调用现有豆包多模态模型进行一次离线分析，输出结构化 JSON。分析结果不直接面向客户，而是作为检索和决策依据。

建议分析维度：

- 这张图是什么类型。
- 图中主体是什么。
- 是否包含可读文字，文字内容是什么。
- 适合回答哪些客户问题。
- 不适合在哪些场景发送。
- 是否包含价格、活动、二维码、水印、隐私信息等风险内容。
- 给出 3 到 8 个检索标签。

如果多模态分析失败，图片可以先入库为 `needs_review`，不参与自动推荐，避免错误素材进入回复链路。

### 19.4 检索与推荐逻辑

图片素材检索应与文本知识库并行，而不是替代文本知识库。

推荐链路：

```text
客户最新入站消息
  -> 提取最新明确咨询问题
  -> 文本知识库检索文档片段
  -> 图片素材库检索候选图片
  -> 大模型生成文字回复
  -> 同时返回建议附图列表、推荐原因、是否需要人工确认
```

图片检索 query 仍应以客户最新咨询为主，最近 10 条聊天记录只作为上下文参考，不应让很早之前的旧话题影响附图推荐。

省略式图片请求需要先解析商品焦点：

- 如果客户最新消息明确包含型号，例如“可以看下 K87 的图片吗”，直接以 `K87 实拍图 外观图 图片` 作为图片检索 query。
- 如果客户最新消息只是“可以看下图片嘛”“发图看看”“有图吗”这类追问，不直接用原句检索，也不拼接最近 10 条历史；应从最近上下文中寻找最近一个明确且单一的商品型号。
- 如果最近上下文能解析出唯一商品焦点，例如上一轮客服刚推荐了 K87 Pro，则图片检索 query 补全为 `K87 实拍图 外观图 图片`。
- 如果最近上下文只出现过“K87、K98、K68”这类多个型号列表，无法判断客户想看哪一款，则不自动推荐/发送图片，应让文字回复澄清具体型号。
- 当解析出商品焦点后，候选图片还需要做型号过滤；例如焦点是 K87 时，K68/K98 图片即使命中也不能进入建议附图或自动附图。

候选图片排序可以先用轻量方案：

- OCR 文本和摘要关键词命中。
- 标签命中。
- 适用场景命中。
- 关联商品/类目命中。
- 风险标签降权或过滤。

后续可把图片摘要、OCR 文本、标签组合成文本，复用当前 BGE embedding 做语义检索。

#### 19.4.1 近百张弱命名图片的检索增强策略

当图片素材达到几十到近百张，并且文件名类似 `IMG_001.jpg`、`1.jpg`、`截图.png` 这类弱命名时，仅靠“文件名 + 多模态模型生成摘要”检索会不稳定。原因是：

- 文件名无法提供商品型号、配件名称、颜色、角度、用途等强信号。
- 多模态模型离线生成的摘要可能偏泛化，例如“一个键盘配件图片”，不足以精确区分拔键器、轴体、键帽、K87、K98。
- 客户问题通常很短，例如“有图吗”“看下实拍”“这个配件什么样”，需要结合上下文解析焦点。
- 只用文本摘要检索时，可能命中“语义相近但对象错误”的图片，例如客户问 K87，却命中 K68。

因此图片素材库后续应从单路检索升级为多路检索：

```text
客户最新问题 / 图片意图
  -> 解析商品焦点、配件焦点、颜色、图片用途
  -> 文本 metadata 检索：文件名、标题、摘要、OCR、标签、场景、来源 Excel 行
  -> 图文向量检索：用文本 query 直接检索图片 embedding
  -> 规则过滤：商品型号、配件名、风险标签、是否启用
  -> 融合排序：文本分 + 图片向量分 + 关键词强命中 + 场景加权
  -> TopN 候选多模态 rerank
  -> 返回建议附图、推荐原因、置信度和风险提示
```

可借鉴的开源实现思路：

- `OpenCLIP` / `Chinese-CLIP`：把图片和文本映射到同一向量空间，适合“用一句客户问题找图片”。中文客服场景可优先评估 `Chinese-CLIP`。
- `BGE-VL`：多模态 embedding 模型，适合图文检索；可作为当前 BGE 文本向量能力的后续扩展方向。
- `Qdrant` / `LanceDB` 的 CLIP 图搜图、文搜图示例：可借鉴“图片向量入库 + 文本向量查询 + topK 排序”的工程结构。
- `LlamaIndex` 多模态 RAG 思路：文本知识库和图片向量库分开建索引，查询时并行检索，再把候选结果交给大模型综合判断。

当前项目不需要马上引入完整多模态 RAG 框架。近百张图片规模很小，本机 SQLite + 内存向量排序仍可接受。更重要的是把图片素材档案做完整，并把检索信号拆清楚。

图片入库时建议增加或强化以下字段：

- `image_embedding`：图片本身的多模态向量。
- `embedding_model`：例如 `chinese-clip-vit-base`、`bge-vl-base`，便于后续重建和兼容。
- `canonical_title`：系统生成的规范标题，例如 `K87 黑红配色正面实拍图`。
- `object_focus`：主要对象，例如 `K87`、`拔键器`、`键帽`、`轴体`。
- `product_model`：商品型号，例如 `K87`、`K98 Max`、`K68 Lite`。
- `color_style`：颜色或风格，例如 `黑红`、`灰白`、`青白`。
- `view_angle`：图片角度或用途，例如 `正面`、`细节`、`尺寸图`、`安装说明`。
- `source_ref`：来源文档、Excel 行号或快捷短语编码，方便把“文档片段中有图片名”和“图片素材”关联起来。

融合排序建议：

```text
final_score =
  0.35 * image_vector_score
  + 0.25 * text_metadata_score
  + 0.20 * exact_object_or_model_bonus
  + 0.10 * scenario_bonus
  + 0.10 * source_link_bonus
  - risk_penalty
```

其中：

- `image_vector_score` 来自图文向量检索，解决弱命名图片的召回问题。
- `text_metadata_score` 来自摘要、OCR、标签、来源行的关键词/文本向量命中。
- `exact_object_or_model_bonus` 用于强约束商品型号和配件名，避免 K87 问题命中 K68 图片。
- `scenario_bonus` 用于区分实拍图、尺寸图、安装图、售后说明图。
- `source_link_bonus` 用于强化文档片段中的 `图片名=xxx.jpg`、Excel 行图片链接等已知关联。
- `risk_penalty` 用于过滤或降权水印、二维码、旧价格、旧活动、隐私信息等风险素材。

TopN 候选图片可以再交给多模态模型做轻量 rerank。输入不需要是全部图片，只需要 3 到 5 张候选图及其素材档案，让模型判断：

```text
客户当前想看的是什么？
候选图片中哪张最匹配？
是否存在商品型号/配件对象不一致？
是否有水印、二维码、价格活动等发送风险？
是否建议附图？推荐原因是什么？
```

这样可以避免让大模型在近百张图片中直接“盲选”，同时提升可解释性和成本可控性。

分阶段落地建议：

1. 短期：继续使用现有多模态分析摘要、OCR、标签，并强化 `object_focus/product_model/source_ref` 等结构化字段。
2. 中期：接入开源图文 embedding，例如 `Chinese-CLIP` 或 `BGE-VL`，为图片生成离线向量。
3. 中期：图片检索改成“文本 metadata 检索 + 图文向量检索 + 规则融合排序”。
4. 后期：对 TopN 候选调用豆包多模态 rerank，输出建议附图、置信度、推荐原因和风险提示。
5. 后期：在后台 UI 增加素材人工校正能力，允许人工修改标题、标签、商品型号、适用场景和风险标签。

首版仍保持“建议附图 + 人工确认”优先。只有当图文向量检索、规则过滤和风险标签稳定后，才把低风险场景开放给自动发图。

### 19.5 自动发送边界

PoC 阶段建议只做“推荐附图”，不直接自动发送图片。

可以推荐附图的低风险场景：

- 客户明确问“有实拍图吗”“发图看看”。
- 客户问尺寸、规格、配列、安装方式，且素材库有明确对应说明图。
- 客户问颜色、外观、图案效果，且素材库命中对应商品实拍图。

不建议自动发图的场景：

- 价格、活动、优惠券相关图片。
- 售后争议、投诉、退款、退货场景。
- 图片与当前商品或问题匹配不确定。
- 图片含旧价格、旧活动、平台水印、二维码、隐私信息。
- 客户没有表达看图需求，且文字已足够回答。

当系统推荐附图时，聚合 UI 应展示：

```text
建议附图：xxx.jpg
推荐原因：客户在问键帽实拍效果，该图是对应商品实拍图。
风险提示：无 / 含活动信息，需人工确认。
```

客服确认后再发送。只有在命中准确率稳定、风险标签完善后，才考虑给部分低风险场景开放自动附图。

### 19.6 与现有 AI 回复链路的关系

图片素材库不应重写一套 AI 回复逻辑，而是扩展现有“生成本条回复”和“AI 自动回复”链路：

- 文本回复仍由现有 `AiChatAppService` 组装 prompt 并调用大模型。
- 图片素材检索结果作为额外上下文或结构化候选项传入。
- 大模型可以给出“是否建议附图”和“建议附图原因”，但最终发送动作先由 UI 人工确认。
- trace 日志需要记录图片检索 query、候选图片、风险标签、推荐原因和最终是否发送。

这样可以先把图片作为可解释、可控的客服素材管理起来，再逐步演进到更自动化的附图回复能力。

### 19.7 素材目录同步与去重规则

日期：2026-07-03

图片素材库导入后，UI 的“刷新素材”读取的是数据库中的素材记录，而不是直接扫描 `docs/knowledge-base` 源目录。因此必须明确数据库记录与源目录之间的同步规则，否则会出现以下问题：

1. 源目录中的图片已经删除，但数据库里的素材记录仍然是 `enabled=1`，后台刷新后仍会显示旧图片。
2. 源目录中的图片只是改名，内容 hash 不变，但旧逻辑按“文件名 + hash”匹配，会把同一张图片重复导入。
3. 历史临时图、预览图或测试图曾经导入过，源目录清理后仍留在素材列表中。

本阶段修正原则：

- 图片素材记录需要保存 `source_path`，表示本次导入时对应的源目录文件路径。
- `file_path` 仍表示系统复制到 `database/knowledge_files/` 下的内部文件路径，用于后续发送和预览。
- `source_path` 用于判断素材是否仍属于当前导入目录，不能和 `file_path` 混用。
- 目录导入/重建完成后，应执行一次图片素材同步。

同步规则：

```text
读取当前导入目录下的图片文件
  -> 生成 current_names 和 current_source_paths
  -> 遍历当前知识库中 enabled=1 的图片素材
  -> 如果 source_path 存在，则以 source_path 是否仍在 current_source_paths 判断是否保留
  -> 如果 source_path 为空，则兼容旧数据，以 original_filename 是否仍在 current_names 判断是否保留
  -> 不在当前目录快照中的素材置为 enabled=0
  -> 对仍启用的素材按 content_hash 去重，只保留最新一条
```

重复导入规则：

- 优先按 `base_id + original_filename + content_hash` 查找完全相同素材。
- 如果没有完全命中，再按 `base_id + content_hash` 查找同内容素材。
- 这样图片改名后不会生成重复素材，而是更新同一条素材记录的 `original_filename`、`source_path` 和分析结果。

刷新素材的产品语义：

- “刷新素材”只刷新当前数据库状态，不主动重新扫描源目录。
- 用户点击“导入/重建知识库”后，才会以当前目录为准同步素材。
- 如果源目录删除了图片，重新导入/重建后该图片应从素材列表消失。
- 如果源目录中图片改名但内容不变，重新导入/重建后素材列表应只显示新文件名，不应同时显示旧文件名和新文件名。

当前测试目录 `docs/knowledge-base` 的期望图片素材为 6 张：

```text
keyboard_k68_mellow_cyan_white_detail.jpg
keyboard_k68_mellow_cyan_white_scene.jpg
keyboard_k87_inphic_black_red_front.png
keyboard_k87_inphic_gray_white_front.png
keyboard_k98_kzzi_blue_white_front.jpg
keyboard_k98_kzzi_retro_front.png
```

验收标准：

- 导入当前 `docs/knowledge-base` 后，后台素材列表只显示上述 6 张启用图片。
- `knowledge_image_assets` 中启用记录不应存在重复 `content_hash`。
- 删除源目录图片并重新导入后，对应素材记录应置为 `enabled=0`。
- 图片改名并重新导入后，只保留改名后的素材记录。
- 单元测试覆盖“源目录变化后下架旧图”和“同内容改名不重复导入”。

## 20. 可切外部 Linux 知识库服务

当前小型知识库服务虽然先以内置 Python sidecar + SQLite + 本地文件目录实现，但架构上应保留后期切换到外部 Linux 知识库服务的空间。这里的目标不是马上替换当前实现，而是在接口和职责边界上避免把 C++ 聚合界面绑定到某一个具体知识库实现。

### 20.1 推荐架构

推荐继续让 C++ 侧只调用本机 Python sidecar，由 Python sidecar 决定实际使用本地知识库还是远端知识库。

```text
C++ 聚合界面
  -> IpcService
  -> 本机 Python sidecar
  -> local backend: SQLite + 本地 embedding + 图片素材库
  -> remote backend: Linux 知识库服务 / RAGFlow / Qdrant / 自研 RAG API
```

不建议 C++ 聚合界面直接调用 Linux 知识库服务。原因是远端服务会涉及网络超时、鉴权、重试、错误分类、返回格式兼容和降级策略，如果这些逻辑写进 C++ UI 层，后续维护成本会更高。

### 20.2 Backend 抽象

Python sidecar 内部可以把知识库能力抽象成 backend：

```text
KnowledgeBackend
  search(query, platform, shop_id, scene, top_k, timeout_ms)
  search_images(query, platform, shop_id, scene, top_k, timeout_ms)
  list_documents(base_id)
  list_images(base_id)
  import_directory(base_id, directory)
```

首版 backend：

```text
local:
  使用当前 KnowledgeStore
  SQLite 存元数据、chunk、embedding、图片素材
  database/knowledge_files 存原始文件和图片副本
```

后续 backend：

```text
remote:
  Python sidecar 转发请求到 Linux 知识库服务
  把远端返回转换成当前 C++ 已经适配的统一 JSON 格式
```

这样 C++ 聚合界面、Prompt 注入、trace 日志、建议附图和 AI 自动回复链路都可以保持不变。

### 20.3 配置建议

建议通过环境变量或本地配置控制 backend：

```text
AI_CUSTOMER_SERVICE_KNOWLEDGE_BACKEND=local
AI_CUSTOMER_SERVICE_KNOWLEDGE_BACKEND=remote

AI_CUSTOMER_SERVICE_KNOWLEDGE_REMOTE_BASE_URL=http://linux-server:8765
AI_CUSTOMER_SERVICE_KNOWLEDGE_REMOTE_API_KEY=可选
AI_CUSTOMER_SERVICE_KNOWLEDGE_REMOTE_TIMEOUT_MS=2500
AI_CUSTOMER_SERVICE_KNOWLEDGE_REMOTE_FALLBACK_LOCAL=1
```

默认仍使用 `local`，保证开发机离线可用。只有明确配置 `remote` 时才转发到 Linux 服务。

### 20.4 接口兼容要求

远端服务返回格式应尽量兼容当前本地接口。

文本检索接口保持：

```text
POST /api/knowledge/search
```

返回核心字段：

```json
{
  "status": "success",
  "results": [
    {
      "source_id": "doc-xxx",
      "chunk_id": "chunk-xxx",
      "source_title": "文档标题",
      "title_path": "章节路径",
      "snippet": "原文片段",
      "score": 0.86,
      "match_type": "hybrid",
      "metadata": {
        "keyword_score": 0.8,
        "vector_score": 0.7,
        "embedding_model": "..."
      }
    }
  ],
  "metadata": {
    "mode": "hybrid",
    "latency_ms": 120
  }
}
```


返回核心字段：

```json
    {
      "asset_id": "img-xxx",
      "source_title": "keyboard_k87_inphic_black_red_front",
```

### 20.5 降级策略

远端知识库服务不可用时，不应阻断 AI 回复生成。

建议策略：

1. remote 请求失败、超时、返回格式不合法时，记录 trace：`remote_http_timeout`、`remote_server_error`、`remote_bad_response`。
2. 如果 `AI_CUSTOMER_SERVICE_KNOWLEDGE_REMOTE_FALLBACK_LOCAL=1`，自动回退本地 `KnowledgeStore`。
3. 如果本地也失败，按当前无知识库链路生成回复。
4. trace 日志记录 backend、远端耗时、失败阶段、是否 fallback、最终注入了多少条片段。

### 20.6 分阶段外部化

推荐分阶段切换，不需要一次性把全部能力迁移到 Linux。

阶段一：文本检索远端化

```text
文档导入和图片素材仍走本地
文本 /api/knowledge/search 可配置转发到 Linux
图片 /api/knowledge/images/search 仍走本地素材库
```

阶段二：embedding 和向量库远端化

```text
Linux 服务负责 embedding、向量索引、BM25、rerank
Python sidecar 只负责代理、鉴权、格式转换和 fallback
```

阶段三：完整知识库平台化

```text
接入 RAGFlow / Qdrant / Chroma / 自研知识库平台
后台管理 UI 可选择本地知识库或远端知识库
导入、删除、重建、权限、租户隔离由远端平台承担
```

### 20.7 验收标准

- C++ 聚合界面不直接依赖远端知识库地址和鉴权细节。
- 切换 `local/remote` backend 不改变聚合界面的调用方式。
- 远端服务返回的文本片段能继续注入现有 Prompt。
- 远端失败时能降级，不影响“生成本条回复”和“AI 自动回复”的基本可用性。
- trace 日志能看出本次使用的是 `local` 还是 `remote`，以及远端耗时和失败阶段。
- 图片素材库可以先继续本地化，文本知识库先远端化，不要求一次性完整迁移。
