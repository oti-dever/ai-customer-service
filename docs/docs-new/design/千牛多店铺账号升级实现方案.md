# 千牛多店铺账号升级实现方案

## 1. 背景

当前千牛自动化链路已经支持在一个千牛接待窗口内监听会话、切换买家会话、读取消息并回写发送。现有测试环境主要是单店铺账号，千牛窗口顶部没有明显的多账号标签栏；在多店铺登录场景下，窗口顶部会出现店铺账号 tab，自动化链路在切换买家会话前还需要先切换到目标店铺。

这次升级不宜一开始直接修改主监听和发送链路。单账号和多账号界面存在结构差异，且顶部店铺 tab 是否稳定暴露 UIA 属性还需要实机验证。推荐先做独立探测，证明能拿到多个账号名、能识别当前选中账号、能点击顶部 tab 切换店铺，再把结果抽象进千牛 sidecar。

## 2. 目标

1. 支持千牛单窗口内多个店铺账号的自动化管理。
2. 支持识别已登录店铺账号列表，包括账号名、选中状态、位置和原始控件信息。
3. 支持自动切换店铺账号，并在切换后继续复用现有会话扫描、消息读取和发送能力。
4. 支持会话、消息、发送任务按店铺账号隔离，避免不同店铺下同名买家会话混淆。
5. 保持单店铺账号兼容，单账号场景不增加用户感知成本。
6. 为后续店铺级知识库、机器人策略和启停管理留出数据与接口位置。

## 3. 非目标

1. 不把多个店铺账号建成多个并行千牛 adapter。千牛仍是一个前台窗口自动化资源，必须串行切换。
2. 不在第一阶段实现后台协议接入。账号名识别以 UIA 暴露文本为准，不再通过 OCR 识别店铺账号名；截图只用于选中态、未读红点/数字等视觉特征辅助判断。
3. 不要求第一版能无损识别所有隐藏账号或未打开的店铺页面。先覆盖顶部可见 tab。
4. 不在探测阶段改动主监听、发送、数据库迁移和聚合 UI。

## 4. 当前实现基线

### 4.1 Python 千牛 sidecar

当前主要代码：

- `python/rpa/platforms/qianniu/adapter.py`
- `python/rpa/platforms/qianniu/sessions.py`
- `python/rpa/platforms/qianniu/reader.py`
- `python/rpa/platforms/qianniu/sender.py`
- `python/rpa/platforms/qianniu/detector.py`

当前链路假设是：

```text
当前千牛窗口
  -> 当前店铺上下文
  -> 当前会话列表
  -> 切换买家会话
  -> 读取/发送消息
```

其中 `QianniuSidecarAdapter._account_id` 已存在，但现在主要来自命令 payload 或默认值，不来自真实千牛顶部店铺 tab。`_conversation_key(account_id, display_name)` 已按 `qianniu:<account_id>:<display_name>` 生成，具备承载多店铺的基本形态。

### 4.2 C++ 平台适配器

当前主要代码：

- `src/services/platforms/qianniurp_adapter.cpp`
- `src/services/platforms/iplatformadapter.h`
- `src/core/messagerouter.cpp`

C++ 侧 `QianniuRPAAdapter` 通过 WebSocket command 调 Python service，发送时会传：

```json
{
  "platform": "qianniu",
  "account_id": "<adapter accountId()>",
  "command": "send_message",
  "parameters": {
    "conversation_key": "...",
    "display_name": "...",
    "client_message_id": "...",
    "confirm_token": "manual_confirmed_by_agent"
  }
}
```

注意：当前 `IPlatformAdapter::accountId()` 默认返回 `platformName()`，因此千牛 C++ 侧默认传入的可能是 `qianniu`，而 Python 千牛默认常量是 `local_qianniu`。多店铺升级时需要统一账号 ID 规范，避免同一店铺在不同路径下生成不同 conversation key。

### 4.3 数据库基础

现有服务端事实库和客户端缓存库都已经有账号字段：

- `conversations.account_id`
- `qianniu_conversations.qianniu_account_id`
- `qianniu_messages.qianniu_account_id`
- `rpa_events.account_id`

因此第一版不一定要大改消息主表，但需要明确 `account_id` 的来源和稳定性。

## 5. 核心设计

多店铺后的完整链路应改成：

```text
当前千牛窗口
  -> 店铺账号列表
  -> 确保目标店铺账号已选中
  -> 目标店铺下的会话列表
  -> 确保目标买家会话已选中
  -> 读取/发送消息
```

关键原则：

1. 店铺切换是会话切换的前置条件。
2. 所有控件缓存都必须带账号上下文，切换店铺后必须失效。
3. 所有会话 key、消息去重 key、未读处理 key 都必须包含 `account_id`。
4. observer 仍串行执行，避免多个店铺切换和发送命令抢焦点。
5. 单账号场景走兼容路径，不要求顶部 tab 存在。

### 6.3 账号 tab 识别策略

优先级从高到低：

1. **UIA TabItem/Button 路径**：查找顶部区域内可点击控件，读取 `Name`、`Value`、`LegacyIAccessibleName`。当前实测能直接拿到账号名，例如 `有求必应羊羊:王刚`、`萌动彼岸岸:机器人`，因此账号名不再依赖 OCR。
2. **几何路径**：窗口顶部账号 tab 区域内，按蓝色选中块、灰色标签块、关闭按钮和加号按钮附近结构识别。
3. **视觉提示路径**：只用于判断顶部账号 tab 是否存在未读提示，例如红点、红色数字、数字计时；不用于识别账号名。

需要过滤：

- 右上角窗口按钮。
- 加号按钮。
- 顶部功能图标。
- 左侧主导航图标。
- 非账号的客服页签，例如“客服”内容页 tab。

### 6.4 切换验证

点击每个候选账号 tab 后执行：

1. 等待 300 到 800ms。
2. 重新读取账号列表，确认 `selected` 状态变化。
3. 调用现有 `QianniuSessionReader.read_visible_sessions(limit=20)`。
4. 调用现有 `QianniuDetector.find_chat_header_names()`。
5. 输出该店铺下会话数量和当前聊天标题。

验收标准：

- 单账号截图场景：返回 1 个 synthetic account 或 1 个真实账号，不能误判顶部功能按钮。
- 多账号截图场景：返回至少 2 个账号，选中状态正确。
- 点击 tab 后 active account 能变化。
- 切换后现有会话扫描仍可用。
- 探测失败时保存顶部截图和 UIA 树摘要，便于修规则。

## 7. 阶段 B：账号能力抽象

探测稳定后新增账号模块：

```text
python/rpa/platforms/qianniu/accounts.py
```

核心模型：

```python
@dataclass(frozen=True)
class AccountTab:
    account_id: str
    display_name: str
    selected: bool
    has_unread_hint: bool
    unread_badge_text: str
    unread_elapsed_text: str
    unread_hint_rect: tuple[int, int, int, int] | None
    unread_score: float
    rect: str
    rect_tuple: tuple[int, int, int, int] | None
    control: Any | None
    source: str
    confidence: float
    raw_texts: list[str]
```

核心接口：

```python
class QianniuAccountReader:
    def list_accounts(self) -> list[AccountTab]: ...
    def selected_account(self, *, fresh: bool = False) -> AccountTab | None: ...
    def switch_account(self, account_id: str) -> tuple[bool, str]: ...
    def invalidate_cache(self) -> None: ...
```

### 7.1 account_id 生成规则

推荐规则：

1. 如果后续能从千牛拿到稳定店铺 ID，优先使用官方 ID。
2. 当前阶段以顶部 tab 展示名生成稳定本地 ID：

```text
account_id = qnacct_<sha1(normalized_display_name)[:12]>
```

3. 单账号兼容：
   - 没有顶部 tab 时，使用 `local_qianniu`。
   - 如果用户后续在账号管理中确认店铺名，可以把 `local_qianniu` 映射到真实 `qnacct_xxx`，但需要迁移或兼容旧 conversation key。

### 7.2 缓存失效

切换账号后必须失效：

- `QianniuSessionReader.last_chat_root`
- `QianniuSessionReader.last_session_root`
- `QianniuReader.cached_chat_root`
- `QianniuReader.cached_message_display`
- `QianniuReader.cached_message_web`
- `QianniuSender.cached_input_field`
- 当前未读已处理集合中与账号相关的局部状态

建议在 `QianniuSidecarAdapter` 中提供统一方法：

```python
def _invalidate_account_scoped_caches(self) -> None:
    ...
```

### 7.3 顶部账号未读提示

多店铺监听依赖顶部账号 tab 的未读提示来决定是否切换到非当前店铺。实测现象：

- 当前选中店铺来新消息时，顶部账号 tab 通常不出现额外提示，未读特征仍出现在当前会话列表项上，等同原单账号场景。
- 非当前店铺来新消息时，对应账号 tab 会出现红点、红色数字或数字计时，例如 `3秒`。这表示需要先切换店铺，再扫描该店铺会话列表。
- 没有新消息的非当前店铺账号 tab 不应触发切换，避免频繁抢占前台焦点。

第一版只要求识别“是否存在未读提示”，不要求精确解析未读数量或计时文本。推荐字段：

```python
has_unread_hint: bool
unread_badge_text: str       # 能从 UIA 读到时记录，例如 "1"、"3秒"，读不到则为空
unread_elapsed_text: str     # 能区分计时文本时记录，不能区分则为空
unread_hint_rect: tuple | None
unread_score: float          # 红色像素/控件命中等综合得分
```

识别策略：

1. 在账号 tab rect 内优先查找 UIA 子控件文本，过滤账号名自身、关闭按钮、加号按钮和窗口按钮。
2. 在账号 tab rect 内做轻量截图颜色检测，寻找红色圆点或红色数字区域。
3. 只把未选中的账号 tab 的顶部红点/数字作为“需要切店铺扫描”的触发信号；当前选中账号仍以会话列表未读项为准。
4. 账号名仍来自 UIA 文本，不使用 OCR。

### 8.2 发送链路

`send_message` 目标选择顺序：

1. 从顶层 `account_id` 读取目标账号。
2. 如果顶层没有，从 `parameters.account_id` 读取。
3. 如果还没有，从 `conversation_key = qianniu:<account_id>:<display_name>` 解析。
4. 单账号兼容时回退到当前账号或 `local_qianniu`。

发送前执行：

```text
ensure_account_selected(account_id)
  -> invalidate caches if switched
ensure_target_session_selected(display_name, conversation_key)
send_text/send_media
```

关键约束：

1. `ensure_account_selected` 必须先于 `ensure_target_session_selected` 执行。
2. 如果目标账号不是当前选中账号，先点击顶部账号 tab，确认 active account 已变成目标账号，再继续切买家会话。
3. 切店铺成功后必须调用 `_invalidate_account_scoped_caches()`，清理会话列表、消息区、输入框和未读处理缓存。
4. `ensure_account_selected` 失败时必须硬失败，不允许 fallback 到当前店铺继续发送，否则存在严重错发风险。
5. 发送结果事件必须写入目标 `account_id`，而不是 adapter 当前临时账号。

### 8.3 监听链路

多店铺监听第一版建议采用“当前账号原逻辑 + 非当前账号按顶部未读提示触发”的串行策略。

当前选中账号：

```text
scan_current_account_sessions(active_account_id)
  -> 沿用现有会话列表未读项识别
  -> 如有未读会话，切会话并读取消息
```

非当前账号：

```text
accounts = list_accounts()
for account in accounts:
  if account.selected:
    continue
  if not account.has_unread_hint:
    continue
  ensure_account_selected(account.account_id)
  scan_current_account_sessions(account.account_id)
```

这种策略的含义：

- 如果当前账号来新消息，顶部账号 tab 没有新特征，仍走原单账号会话列表扫描逻辑。
- 如果非当前账号来新消息，顶部对应账号 tab 出现红点/数字/计时提示，先切店铺，再扫描该店铺会话列表。
- 如果非当前账号没有顶部未读提示，不切过去扫描，避免前台频繁跳动。

第一版每轮每个店铺最多处理一个未读会话，避免一次轮询持有前台窗口过久。后续可以按实测优化为：

- 对顶部未读提示做节流，同一账号短时间内不要重复切换。
- 当前店铺空闲时再扫描其它店铺。
- 多个未读会话批量处理。

建议第一版 observer 伪代码：

```python
def scan_unread_multi_account():
    accounts = account_reader.list_accounts(fresh=True)
    active = selected_account(accounts)

    if active:
        scan_unread_and_fetch_for_account(active.account_id)

    for account in accounts:
        if account.selected:
            continue
        if not account.has_unread_hint:
            continue
        ok, detail = account_reader.switch_account(account.account_id)
        if not ok:
            emit_account_health(account, status="degraded", detail=detail)
            continue
        scan_unread_and_fetch_for_account(account.account_id)
```

这里的 `scan_unread_and_fetch_for_account` 内部仍复用现有单账号会话扫描、切会话和读消息能力，只是所有事件、去重 key 和 handled key 都必须带入当前 `account_id`。

### 8.4 未读处理隔离

当前 `_handled_unread_session_keys` 是按会话标题记录。多店铺后必须改为：

```text
handled_key = f"{account_id}:{normalize_session_title(title)}"
```

否则 A 店铺处理过 `tb123` 后，B 店铺同名 `tb123` 可能被误跳过。

### 8.5 conversation_key

统一使用 canonical key：

```text
qianniu:<account_id>:<display_name>
```

所有路径都应保留完整 key。展示名只用于 UI 展示和会话标题匹配，不作为唯一主键。

### 8.6 当前主链路接入状态

当前已在 Python 千牛 sidecar 主链路接入账号上下文调度，范围包括：

1. `scan_unread_and_fetch`：
   - 每轮先探测顶部账号 tab。
   - 如果非当前账号存在 `has_unread_hint=True`，先切换到该账号，再复用原会话列表未读扫描、切会话、读消息链路。
   - 如果没有顶部账号未读提示，继续扫描当前账号会话列表，保持单账号行为。
   - `_handled_unread_session_keys` 已改为 `account_id + normalized_session_title`，避免不同店铺同名买家互相影响。

2. `fetch_visible_messages`：
   - 从 `conversation_key = qianniu:<account_id>:<display_name>` 或账号参数解析目标账号。
   - 先确保目标账号已选中，再确保目标会话已选中，最后读取消息。

3. `prepare_reply_draft` / `send_message`：
   - 发送或填草稿前先执行账号切换，再执行会话切换。
   - 账号切换失败时直接失败，不继续在当前店铺发送。
   - 发送结果事件和 `message_sent` 事件使用目标 `account_id` 和 canonical `conversation_key`。

4. 单账号兼容：
   - 如果探测不到真实账号 tab，或只有 synthetic single account，保留旧单账号链路。
   - 旧调用中传入外部 `account_id` 但没有顶部账号 tab 时，不强制失败。

当前尚未接入：

- `list_accounts` / `switch_account` / `probe_accounts` 对外 command。
- 聚合界面的千牛账号管理入口。
- 店铺账号启停管理、机器人绑定和持久化账号表。
- 多个非当前账号未读的批量轮询；第一版每轮优先处理一个顶部未读账号。

### 8.7 低并发场景下的串行任务队列优化方案

当前多账号主链路已经能完成“顶部账号未读探测 -> 切换店铺 -> 扫会话列表 -> 切会话 -> 读取消息 -> 发送回复”，但通用链路仍存在一个明显成本：监听、读消息和发送回复可能交错发生。读完 A 会话后，如果 observer 又发现 B 会话未读，发送 A 回复时就需要重新确认账号、重新扫会话列表、重新找回 A 会话，导致耗时增加，也增加 UIA 状态不确定性。

在“只监听千牛平台 + 日常客流低并发”的假设下，可以把千牛链路简化为“单 UI 工作者 + 会话任务队列”。

适用假设：

1. 当前只开启千牛平台监听，或千牛平台内部可以独占自身 UIA 自动化上下文。
2. 客流量不高，同一分钟内多个客户同时咨询的概率较低。
3. 优先保证单个会话从读取到回复的上下文稳定，而不是在一次扫描中尽可能多地切换账号和会话。
4. 新消息可以排队处理，不要求打断当前正在处理的会话。

核心模型：

```text
QianniuUnreadScanner
  -> 发现当前账号会话未读 / 顶部账号 tab 未读
  -> 生成 QianniuConversationTask
  -> 入队 QianniuConversationTaskQueue

QianniuConversationWorker
  -> 串行取队首任务
  -> 独占千牛 UI
  -> 切店铺账号
  -> 扫一次目标账号会话列表
  -> 点击目标会话
  -> 读取聊天消息
  -> 等待 AI 回复
  -> 直接在当前输入框发送
  -> 处理下一个任务
```

任务结构建议：

```python
class QianniuConversationTask:
    task_id: str
    account_id: str
    account_display_name: str
    session_title: str
    conversation_key: str
    source: str              # current_session_unread / top_account_unread / manual_send 等
    created_at: float
    attempt: int
    last_unread_hint: dict | None
```

队列去重规则：

```text
dedupe_key = f"{account_id}:{normalize_session_title(session_title)}"
```

同一个 `dedupe_key` 已在队列中或正在处理中时，不重复入队；如果客户在同一会话继续发消息，保留同一个任务，处理时重新读取当前聊天区最新消息即可。

扫描器职责：

1. 空闲时扫描当前选中账号的会话列表未读，发现未读会话后入队。
2. 空闲时探测顶部账号 tab 未读，发现非当前账号有未读提示后入队账号级任务。
3. 如果顶部 tab 只能知道“某账号有未读”，但还不知道具体客户会话，任务可以先只携带 `account_id`，由 worker 切过去后扫一次会话列表并定位未读会话。
4. scanner 不负责读取聊天消息，不负责发送消息，也不在 worker 处理期间频繁切账号或切会话。

worker 处理流程：

```text
dequeue task
  -> ensure_account_selected(task.account_id)
  -> scan_current_account_sessions_once(task.account_id)
  -> resolve target unread session
  -> click target session
  -> read visible messages
  -> emit conversation/message events
  -> wait/generate AI reply through existing pipeline
  -> send reply through current input box
  -> mark task done
```

关键约束：

1. worker 开始处理任务后，直到当前会话回复完成，不被其它账号或其它会话的新消息抢占。
2. worker 处理期间，scanner 默认暂停侵入式扫描；第一版可以直接暂停 scanner，等 worker 完成后再扫下一轮。
3. 如果需要在 worker 处理期间记录其它账号新消息，只允许做非侵入式记录，例如读取已经缓存的顶部 tab 未读状态；不能切换账号或会话。
4. worker 内的发送路径不再重新执行完整的“切账号 -> 扫会话 -> 切会话”兜底，因为当前 UI 上下文就是刚读完的目标会话。
5. 如果发送命令来自聚合界面人工操作，而不是当前 worker 正在处理的任务，仍保留现有安全路径：必须确认目标账号和目标会话后才能发送。

发送直通规则：

```text
worker_task_send:
  if current_task still active
     and selected_account == task.account_id
     and selected_session == task.session_title:
       resolve current input box
       paste/type reply
       send
  else:
       fail safe or fallback to ensure_target_session_selected
```

也就是说，自动回复链路中“读完当前会话后立即回复当前会话”应走直通路径，避免依赖 active context TTL，也避免每次发送都触发完整 UIA 会话列表扫描。

失败和重试：

1. 切账号失败：标记任务失败，记录账号名、目标账号、失败阶段和 UIA 详情；不发送。
2. 找不到会话列表或目标会话：标记任务失败，可等待下一轮扫描重新发现；不发送。
3. 读取消息失败：不进入 AI 回复；可有限重试一次。
4. 输入框或发送失败：记录失败阶段，可保留任务或由人工接管；不重复盲发。
5. 停止监听时必须停止 scanner 和 worker，并清空或持久化未完成任务，不能让旧健康探测线程或旧 worker 阻塞下一次启动。

预期收益：

1. 减少发送阶段重新找账号、重新扫会话列表、重新切会话的耗时。
2. 降低 UIA 锁竞争，observer 不再和发送线程互相抢上下文。
3. 不再依赖较短的 active context TTL 判断“当前会话是否还有效”。
4. 行为更接近人工客服：打开一个客户，读完，回复完，再处理下一个客户。

风险和取舍：

1. 当前任务处理期间，新来的其它账号消息会等待，低并发场景可接受。
2. 如果 AI 回复耗时较长，队列等待时间会变长，需要在日志中记录任务排队耗时和处理耗时。
3. 用户手动操作千牛窗口仍可能破坏 worker 当前上下文，因此发送前仍要做最低限度的账号和会话一致性校验。
4. 后续如果客流量上升，可以再扩展为按账号分片队列或更激进的批量扫描，但第一版不建议增加复杂度。

建议分阶段落地：

1. 先保留现有主链路，增加队列模型日志字段：`task_id`、`dedupe_key`、`queue_wait_ms`、`process_ms`、`send_direct_path`。
2. 引入内部 `QianniuConversationTaskQueue`，让 scanner 只负责发现和入队。
3. 引入 `QianniuConversationWorker` 串行消费任务，处理期间暂停侵入式扫描。
4. 自动回复发送接入 worker 直通路径；人工发送继续走现有安全路径。
5. 稳定后再考虑输入框缓存、当前 chat root 缓存和账号级并发策略。

## 9. 阶段 D：店铺账号管理

### 9.1 聚合界面账号管理入口

聚合界面左侧千牛平台按钮增加右键菜单：

```text
千牛平台按钮右键
  -> 管理账号
```

点击“管理账号”后弹出账号管理对话框。第一版只做只读展示：

1. 调用 Python sidecar 的账号探测能力，读取当前千牛已登录店铺账号。
2. 对话框只展示店铺账号名列表，例如：
   - `有求必应羊羊:王刚`
   - `萌动彼岸岸:机器人`
3. 不展示账号 ID、当前是否选中、顶部未读提示、最近扫描时间、最近状态等字段。
4. 不做启用/禁用选择；第一版所有已登录店铺账号统一视为启用监听。
5. 可以保留“刷新”动作，重新读取当前千牛窗口的账号列表。

第一版账号管理对话框的目标只是让用户确认“当前系统识别到了哪些千牛店铺账号”。账号启停、别名、健康状态、最近消息时间都放到后续阶段。

### 9.2 会话列表店铺来源展示

多店铺后，聚合接待的千牛会话列表必须让客服能区分会话来源店铺。展示规则：

```text
<客户名>（<店铺账号名>）
```

示例：

```text
tb4947894539（有求必应羊羊:王刚）
```

约束：

1. UI 展示可以拼接店铺账号名，但内部主键仍必须使用 canonical conversation key：

```text
qianniu:<account_id>:<display_name>
```

2. 发送目标仍从 `conversation_key` 解析 `account_id`，不能依赖展示字符串反解析。
3. 如果千牛会话事件能提供 `metadata.account_display_name`，优先展示该值。
4. 如果暂时没有店铺账号名，可退回显示原客户名，不能阻塞消息展示。
5. 非千牛平台展示规则不变。

机器人绑定暂不在本阶段实现。后续可以扩展为：

- 平台级默认机器人。
- 店铺账号级机器人。
- 店铺账号 + 会话标签/客户分组级机器人。

### 9.3 后续数据表建议

第一版账号管理入口只读展示账号名，不需要新增持久化表。后续如果要支持账号启停、别名、机器人绑定和健康状态，再新增平台账号表：

```sql
CREATE TABLE IF NOT EXISTS platform_accounts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  platform TEXT NOT NULL,

  last_seen_at DATETIME,
  last_selected_at DATETIME,
  health_status TEXT DEFAULT '',
  raw_payload_json TEXT DEFAULT '',
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,

);
```

后续知识库绑定可从平台级扩展到账号级：


## 10. API 和事件约定

### 10.1 account_health_changed

多店铺后健康事件可以分两类：

1. 平台整体健康：千牛进程、窗口、自动化能力是否可用。
2. 账号健康：某个店铺是否可切换、是否可读取会话列表。

事件建议：

```json
{
  "event_type": "account_health_changed",
  "platform": "qianniu",
  "account_id": "qnacct_xxx",
  "payload": {
    "status": "online",
    "healthy": true,
    "display_name": "有求必应羊羊:王刚",
    "metadata": {
      "selected": true,
      "switch_method": "rect_click"
    }
  }
}
```

### 10.2 conversation_observed

必须包含：

```json
{
  "platform": "qianniu",
  "account_id": "qnacct_xxx",
  "conversation_key": "qianniu:qnacct_xxx:tb4947894539",
  "payload": {
    "display_name": "tb4947894539",
    "metadata": {
      "account_display_name": "有求必应羊羊:王刚"
    }
  }
}
```

### 10.3 send_message

建议调用方传入：

```json
{
  "platform": "qianniu",
  "account_id": "qnacct_xxx",
  "command": "send_message",
  "parameters": {
    "conversation_key": "qianniu:qnacct_xxx:tb4947894539",
    "display_name": "tb4947894539",
    "text": "你好",
    "confirm_token": "manual_confirmed_by_agent"
  }
}
```

Python 侧即使从 `conversation_key` 解析到了 account，也要在日志里记录最终目标账号，便于排查错发风险。

## 13. 风险与处理

| 风险 | 影响 | 处理 |
| --- | --- | --- |
| 顶部 tab 不暴露 UIA 文本 | 无法直接拿账号名 | 当前实测已能拿到账号名；若后续版本变化，优先补 UIA/几何规则，OCR 不作为账号名第一版方案 |
| 顶部未读红点/数字识别误判 | 误切店铺或漏扫非当前店铺 | 只在非当前账号 tab rect 内做红色视觉检测，并结合 UIA 子控件文本；失败时保存顶部截图和 JSON |
| 店铺名变化 | account_id 不稳定 | 引入人工别名和映射表，后续寻找更稳定 ID |
| 切换账号后旧控件仍可访问但已指向旧页面 | 读写错账号 | 切换后统一 invalidate 缓存并重新定位 |
| 同名买家存在于不同店铺 | 会话混淆 | conversation key 必须包含 account_id |
| observer 正在扫描时用户手动切 tab | 状态漂移 | 每次读写前重新确认 active account |
| 多店铺轮询导致前台频繁跳动 | 影响客服手动操作 | 当前账号走原会话列表扫描；非当前账号只有顶部有未读提示才切换；账号启停和扫描频率控制放到后续阶段 |
| 切店铺失败后继续发送 | 严重错发 | `ensure_account_selected` 失败必须硬失败，不允许 fallback 到当前店铺发送 |

## 14. 实施顺序

推荐按以下顺序推进：

1. 新增独立探测脚本，不改主链路。
2. 用实机单账号、多账号截图验证账号 tab 识别。
3. 固化 `accounts.py`，补单元测试。
4. 为 `AccountTab` 增加 `has_unread_hint`、`unread_badge_text`、`unread_hint_rect`、`unread_score` 等字段，并用实机验证“无提示/非当前账号有提示/当前账号有会话未读”三类场景。
5. 为 `QianniuSidecarAdapter` 增加 `list_accounts` 和 `switch_account` 命令。
6. 发送链路接入 `ensure_account_selected`，先覆盖人工发送。
7. observer 接入多店铺串行轮询：当前账号走原逻辑，非当前账号只在顶部有未读提示时切换扫描。
8. 聚合左侧千牛平台按钮增加“管理账号”右键菜单，弹窗只读展示当前已登录店铺账号名。
9. 聚合会话列表展示千牛店铺来源，例如 `tb4947894539（有求必应羊羊:王刚）`。
10. 后续再增加账号启停、持久化表和店铺级知识库/机器人绑定。

## 15. 第一阶段完成定义

第一阶段只要求完成探测 PoC，不要求接入主链路。完成标准：

1. 能在多店铺千牛窗口中输出账号列表。
2. 能识别当前选中账号。
3. 能点击切换顶部账号 tab。
4. 切换后能重新读取当前店铺下的会话列表。
5. 单店铺窗口不会误判多个账号。
6. 失败时有截图、UIA 摘要和 JSON 结果可分析。

第一阶段通过后，再进入发送链路和 observer 链路改造。
